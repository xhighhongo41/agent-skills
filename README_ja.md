# agent-skills

コーディングエージェント向けの個人用 [Agent Skills](https://agentskills.io) を
1つのリポジトリにまとめ、複数のエージェント・複数のマシンで同一の内容を保つためのものです。

English: **[README.md](README.md)**

> スキル本文は日本語で書いています。英語なのはこの README だけです。
> 作者自身がスキルを頻繁に編集して改良しており、日本語の方が作業が速いという理由による意図的な選択です。
> 構造とメタデータは Agent Skills 標準に従っているので、対応エージェントでは問題なく読み込まれます。

## 対応エージェント

[Agent Skills](https://agentskills.io) オープン標準に準拠しており、以下で動作を確認しています。

| エージェント | スキルの配置先 |
|---|---|
| [Claude Code](https://code.claude.com) | `~/.claude/skills/`（Windows: `%USERPROFILE%\.claude\skills\`） |
| [OpenAI Codex](https://learn.chatgpt.com/docs/build-skills) | `~/.codex/skills/`（`$CODEX_HOME` 設定時はその配下）。Codex は `~/.agents/skills/` も読みます（OpenCode も読む場所です） |
| [OpenCode](https://opencode.ai) | `~/.config/opencode/skills/`（Windows も同じパス） |

Agent Skills 形式を読む他のツールでも動作するはずです。

## 収録スキル

| スキル | 対象 | 内容 |
|---|---|---|
| `python-coding` | 共通 | Python の実装・修正・レビュー時に、PEP 8/257/484、型ヒント、docstring、単一責任を重視した一貫した方針を適用します。テストはプロジェクトに明記された方針、次に既存テストの流儀に従い、どちらも無ければ pytest 準拠で書きます。例外・標準ライブラリの慣用・import の構成・設定値と秘密情報の指針も含みます。 |
| `test-driven-development` | 共通 | テストを先に書く手順。シグネチャ → テスト → 失敗することの確認 → 実装の順に進めます。新規実装・更新実装・バグ修正の3つの進め方と、テスト自体が誤っていると思われるときの判定手順を含みます。 |
| `japanese-writing` | 共通 | 日本語の文書を、段階を分けて書く・直すための手順。書く前と書いている最中に構成・内容・文体を決め、下書きの後に文の表面を1か所ずつ直して、検査スクリプトで確かめます。段階ごとに別の外部スキルを参照物として読み（書く側は natural-japanese、推敲側は yomiyasu）、2つが食い違ったときの決め方も定めています。使うのはファイルに保存する文書を書く・直すときと、利用者が名前を挙げて使用を求めたときで、日常の回答には使いません。 |
| `english-writing` | 共通 | 同じことを英語の文書で行います。読み手・目的・文書の種類・範囲の取り決めと、書き方の規則は technical-documentation に従い、書き終えた下書きは humanizer に通して、AI が書いた文に出やすい書き癖を取り除きます。推敲の前に事実を一次情報と照らし合わせ、根拠の無いことは書き足しません。スキル本文は日本語です。 |
| `project-start` | 共通 | 新規プロジェクトの開始手順。ディレクトリがクローンかローカル作成かを確かめ、ホスティング CLI のアカウントとコミット識別子をリポジトリの所有者に合わせ、進行根幹ファイルと git 非追跡の内部資料置き場、エージェントの固有指示ファイル、ライセンス、`.gitignore` を整えて、初回コミットと push まで行います。各手順は現状を調べて不足だけを行うので、完了後や中断後に再実行しても安全です。 |
| `version-start` | 共通 | 新バージョンの開始手順。着手前に版の状態（未着手・着手済み・リリース済み、飛び越しや別プロジェクトの番号）を照合してから、プロジェクト文書と申し送り文書の読解、コードベースの把握、ブランチ作成、実装計画書のドラフト作成まで行い、実装には入りません。対応するかを尋ねるのは Critical の申し送りだけです。確認事項はコードを読まなくても答えられる日本語で尋ねます。中断した設計は再開できます。 |
| `version-implement` | 共通 | 確定した計画を完了まで進めます。入場ゲートでの版の状態照合と回答照合、タスクごとの実装サイクル、自走と中断を判定する決定木で動きます。残す申し送りは Critical / Recommended / Optional の3段階に分類します。中断後は実装記録とコミットを突き合わせて正しいタスクから再開し、未コミットの作業は消しません。 |
| `version-release` | 共通 | リリース手順のチェックリスト。入場ゲートで未実装の版やリリース済みの版を止め、途中で止まったリリースは残りのゲートから再開します。バージョン上げ忘れの検出、リポジトリから派生して公開されるもの（パッケージ・コンテナのレジストリ、静的ホスティング、URL で配られるマニフェスト）が新しい版になるかの確認、文書追随の確認、検証、PR、マージ、タグ付与、リリースノートのドラフト作成、リリースで不要になった申し送りの消去まで。 |
| `skill-sync` | 共通 | 自マシンのどのエージェントにどのスキルのどの版が入っているかを一覧し、本リポジトリと比較して、選んだものだけを更新します。ただし**書き込むのは自エージェントのコンフィグディレクトリの中だけ**です。比較の対象は、スクリプトや参照文書を含む、スキルのフォルダ内の全ファイルです。版が同じでも中身が配布元と違う複製は「内容が違う」として知らせ、既定では更新しません。対象エージェントが決まっているスキルは、実行中のエージェントが対象かを確かめ、**対象外なら候補から外します**。エージェントごとに必要・不要なスキルを記憶し、不要なスキルの導入を毎回尋ねません。他者のリポジトリから取り込んだスキルは導入元と突き合わせ、導入元の版・本文・付属ファイルのいずれかが変わっていれば更新として知らせます。スキルが外部の参照物（他者のリポジトリから読む資料）を宣言していれば、導入時に取得し、以後の更新にも追随します。取得したものを配置する前に、新しく入るファイルと変わったファイルを監査し、懸念を報告します。 |
| `register-external-skill` | 共通 | 他者のリポジトリで公開されているスキルを自エージェントに取り込みます。リポジトリを取得して収録スキルを列挙し、別のエージェント向けのものを明示したうえで、配置する内容を監査して懸念を報告します。frontmatter が無い・不整合なときは frontmatter だけを補います（本文は変えません）。導入元を `metadata` に、スキルのほかのファイルのチェックサムの一覧をスキルのフォルダ内に記録するので、以後の更新確認は `skill-sync` がまとめて行えます。 |
| `remove-skill` | 共通 | フォルダの内訳（本体と付属ファイル、取得した参照物、キャッシュと一時ファイル、配置の記録）を示して確認を得てから、導入済みのスキルを自エージェントのスキル置き場から削除します。フォルダごと消し、残っていないことを確かめ、`skill-sync.json` も整合させます。他のエージェントの置き場・配布キャッシュ・プラグイン機構の管理下にあるものは消さず、正規の手段を案内します。 |
| `council` | **OpenCode 専用** | 円卓合議の手順。互いに異なるモデル（司会とも異なり、開発元の異なるものを優先）が同じ議題を独立に考え、全員が一致した論点はその場で確定します（残りが無ければそこで終了）。残りの論点は、別ファイルの相互レビューと、自分へのレビューへの各自の応答を経て、司会（メインセッション）が統合して1つの結論にします。脱落した参加者は別モデルで補充します。各参加者は同じセッションを保ち、入手した資料は目録付きで共有します。 |
| `plugin-update-check` | **OpenCode 専用** | 設定に書かれた npm プラグインについて、導入済みの版とレジストリの最新版を突き合わせ、更新の要否を一覧にします。判定だけを行い、何も変更しません。 |
| `plugin-update-apply` | **OpenCode 専用** | プラグインのキャッシュを削除し、次回起動で新しい版を入れ直します。**削除の前に必ず明示的な承認を求めます**。 |

`version-*` の3つは `PROJECT.md` という進行文書を軸にした一連のワークフロー（開始 → 実装 → リリース）です。
言語やスタックを前提にせず、対象プロジェクトの文書から必要な情報を読み取って動きます。
版をまたぐ申し送りは1つの申し送り文書に Critical / Recommended / Optional の3段階で置き、版の着手時に尋ねるのは Critical だけです。
進行文書には版ごとに短い記載を1つだけ置き、各フェーズがそれを更新します。`project-start` は、この3スキルが働くプロジェクトの土台を整えます。

`test-driven-development` は、あえてこのワークフローから独立させています。
テストを先に書くかどうかは利用者の方針であってスキルが決めることではないため、
`version-implement` は実装の進め方をグローバル指示書に委ねています。
したがって、グローバル指示書には「テストを先に書いて開発する」という方針だけを書き、
手続きそのものは本スキルに任せるという使い方ができます。

`japanese-writing` と `english-writing` は段階を分けて動き、段階ごとに他者が公開しているスキルを参照物として読みます（書く段階に1つ、下書きを推敲する段階に1つ）。
この2スキルが補っているのは、参照物を併用したときに決まらない部分、つまりどの段階でどちらを使うかと、2つが食い違ったときの決め方です。
参照物は本リポジトリには含まれていません。スキルを導入するときに、`skill-sync` が作者のリポジトリから取得します。
仕組みは[更新](#更新)の節の「外部の参照物」で説明し、取得元の4件は[謝辞](#謝辞)に挙げています。

`council` は、エージェントを名指ししているスキル（いずれも OpenCode 専用の3件。ほかの2件は `plugin-update-check` / `plugin-update-apply`）の1つです。
互いに異なるモデル（司会とも異なり、開発元の異なるものが望ましい）のサブエージェントが揃って初めて意味があり、
複数のプロバイダのモデルをサブエージェントに割り当てられるのが OpenCode だからです。
この種のスキルは frontmatter の `compatibility` で対象を宣言し、
`description` の冒頭にも対象を書きます。エージェントが読み込む前に対象を判断できるようにするためです。

## インストール

配置されるファイルはどの方法でも同じです。前半2つはどのエージェントでも使え、
後半3つは各エージェント自身の導入機構です。

| 方法 | 対象 | 更新の届き方 | 呼び出し名 |
|---|---|---|---|
| **A** エージェント自身にやらせる | 全部 | もう一度頼む | `/python-coding` |
| **B** 手動でコピー | 全部 | もう一度コピー、または `skill-sync` | `/python-coding` |
| **C** Codex の `skill-installer` | OpenAI Codex | 入れ直す（バージョン比較機構が無い） | `/python-coding` |
| **D** OpenCode の `skills` の設定 | OpenCode | 自動（版が変わったとき） | `/python-coding` |
| **E** Claude Code の marketplace | Claude Code | `/plugin marketplace update` | `/agent-skills:python-coding` |

**D** と **E** は全スキルが一度に入ります。**A**・**B**・**C** は1スキルずつです。

> **エージェント専用スキルと導入経路の関係。** 方法 **D** が読む `skills/index.json` には
> OpenCode で使えるスキルだけが載っているので、OpenCode で使えないものが届くことはありません。
> 方法 **E** はプラグインであり `skills/` 全体を走査するため、`council` は Claude Code にも入ります。
> 入っても動かないだけなので無視して構いません。**A**・**B**・**C** は1つずつ選ぶ方式なので、
> 上の「対象」列を確認してから選んでください。

> **2つのスキルは、`skill-sync` を実行して導入が完了します。** `japanese-writing` と `english-writing` は、
> 本リポジトリに含まれない参照物を読みます。どの方法で入れた場合も、その後で `skill-sync` を実行してください。
> `skill-sync` が参照物を作者のリポジトリから取得します。取得するまでは、この2スキルは最初の手順で止まり、欠けているものを知らせます。
> 詳しくは[更新](#更新)の節の「外部の参照物」をご覧ください。

### 方法A — エージェント自身にやらせる（いちばん簡単）

以下をエージェントに貼り付けてください。スキル名は適宜置き換えます。

```
https://github.com/xhighhongo41/agent-skills の
`skills/python-coding` フォルダをダウンロードして、
あなたのユーザースキルディレクトリに配置してください。
```

エージェントが自分のスキルディレクトリを知らない場合は、上の「対応エージェント」表の
パスを併せて伝えてください。

### 方法B — 手動でコピーする

```bash
git clone https://github.com/xhighhongo41/agent-skills.git
cd agent-skills

# Claude Code
cp -r skills/python-coding ~/.claude/skills/

# OpenAI Codex
cp -r skills/python-coding ~/.codex/skills/

# OpenCode
cp -r skills/python-coding ~/.config/opencode/skills/
```

`SKILL.md` だけでなく**フォルダごとコピー**してください。各スキルには
`agents/openai.yaml` が同梱されており、Codex ではこれが表示名や例示プロンプトとして
使われます。他のエージェントは無視するだけなので、あっても害はありません。

### 方法C — Codex の `skill-installer` を使う

Codex には GitHub の URL から直接インストールできる `skill-installer` が同梱されています。

```
skill-installer を使って
https://github.com/xhighhongo41/agent-skills/tree/main/skills/python-coding
のスキルを入れて
```

### 方法D — OpenCode の `skills` の設定を使う

OpenCode は本リポジトリから直接スキルを取得し、最新に保つことができます。
`opencode.json` の `skills` の配列に、マニフェストのあるディレクトリを加えてください。

```json
{
  "skills": ["https://raw.githubusercontent.com/xhighhongo41/agent-skills/main/skills"]
}
```

この書き方は OpenCode 1.x と 2.x のどちらでも使えます。以前の設定では `{"skills": {"urls": [...]}}` の形で
URL を書いていました。OpenCode はこの形も受け付けて配列の形に変換するので、既存の設定はそのまま動きます。

OpenCode はそのディレクトリの `index.json` を読み、そこに載っているスキルをすべて
ダウンロードします。スキルの版が変わると自動的に取り直します。

最新を追いかけるのではなく特定のリリースに固定したい場合は、URL の `main` を
`v1.0.0` のようなタグに置き換えてください。

### 方法E — Claude Code の plugin marketplace を使う

```
/plugin marketplace add xhighhongo41/agent-skills
/plugin install agent-skills@xhighhongo41-agent-skills
```

全スキルが1つのプラグインとして入ります。他の方法と違う点が2つあります。

- **スキル名に名前空間が付きます**。`/python-coding` ではなく
  `/agent-skills:python-coding` で呼び出します。素の名前で呼びたい場合は方法A・Bを
  使ってください。プラグイン版と個人コピーは互いを上書きせず共存できます。
- サードパーティのマーケットプレイスは**自動更新が既定でオフ**です。最新にしたいときは
  `/plugin marketplace update xhighhongo41-agent-skills` を実行するか、
  `/plugin` → Marketplaces で自動更新を有効にしてください。

特定のリリースに固定したい場合はタグを付けます。
`/plugin marketplace add xhighhongo41/agent-skills@v1.0.0`

マーケットプレイス名が `agent-skills` ではなく `xhighhongo41-agent-skills` なのは、
Claude Code が素の `agent-skills` を Anthropic 公式マーケットプレイス用に予約しているためです。

### インストールできたかの確認

新しいセッションを開始して `/python-coding`（あるいは `/version-start` など）を実行します。
marketplace（方法E）で入れた場合の名前は `/agent-skills:python-coding` です。

各スキルは初回使用時に次のように宣言します。

```
python-coding スキル v1.1.1 を使用します
```

この行が出れば、スキルが実際に読み込まれていること、そしてどのバージョンが入っているかが分かります。

## 推奨: グローバル指示書に「役割 → サブエージェント」の対応を書く

本リポジトリのスキルはサブエージェントへの委譲を役割名で書いています
（例:「解析専任サブエージェント」「読解役サブエージェント」）。実名を書いていないのは、
配布されるスキルはどの環境にインストールされるか分からず、
どんなサブエージェントが定義されているかを知りようがないからです。

サブエージェントを定義している場合は、グローバル指示書に短い対応表を書いておくと
エージェントが迷いません。指示書のファイルはエージェントごとに異なります。

| エージェント | グローバル指示書 |
|---|---|
| Claude Code | `~/.claude/CLAUDE.md` |
| OpenAI Codex | `~/.codex/AGENTS.md` |
| OpenCode | `~/.config/opencode/AGENTS.md` |

次の程度で十分です。

```markdown
## サブエージェントの役割対応

スキルが役割名でサブエージェントに言及したときは、以下を使う。

- 実装担当サブエージェント → <実装用エージェント名>
- 解析専任サブエージェント（テスト・lint 失敗の要点抽出） → <解析用エージェント名>
- 読解役サブエージェント（資料・ログの読解） → <読解用エージェント名>
- 探索役サブエージェント（コード探索） → <探索用エージェント名>
- Web調査役サブエージェント → <調査用エージェント名>
- 判定役サブエージェント（テストと実装のどちらが誤っているかの判定） → <判定用エージェント名>
```

これは任意です。書かなくても、エージェントは手持ちの汎用サブエージェントで代替するので
動作はします。選択がやや大雑把になるだけです。

## Claude Code と OpenCode を両方使っている場合

OpenCode は Claude Code のスキルディレクトリをそのまま読みます。つまり
`~/.claude/skills/` に入れたスキルは OpenCode からも見えます。二重に入れる必要はありません。
無効にしたい場合は `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1` を設定してください。

## 更新

| 方法 | すること |
|---|---|
| **A**・**B** | インストールをもう一度実行すれば上書きされます |
| **C** | `skill-installer` にもう一度頼みます。バージョン比較機構が無いので、入れ直すことが更新そのものです |
| **D** | 何もしなくて構いません。スキルの版が変わると OpenCode が取り直します |
| **E** | `/plugin marketplace update xhighhongo41-agent-skills` |

今どのバージョンが入っているかを調べるには、本リポジトリの `skill-sync` スキルを
使ってください。導入済みの版を本リポジトリの `index.json` と突き合わせ、版が同じものは中身も照合して、
承認を得たうえで古いものだけを取得・配置します。スキル単位でも、まとめてでも指定できます。

また、エージェントごとに必要なスキルと不要なスキルを記憶します。記憶先は実行したエージェントの
コンフィグディレクトリ直下の小さな `skill-sync.json`（`~/.claude/`、`~/.codex/`、`~/.config/opencode/`）で、
エージェント本体の設定ファイルには書きません。不要と記したスキルの導入は尋ねられなくなり、必要と記したのに
未導入のスキルは導入するかを確認し、不要と記したのに導入済みのスキルは一覧に出すだけで、削除も、名指ししない限り
更新もしません。初回は現在の導入状況から初期値を提案し、確認後に1回で書きます。

**書き込むのは、そのスキルを実行しているエージェント自身のコンフィグディレクトリの中だけ**です。
他のエージェントのスキルを代わりに更新することはありません。別のエージェントを更新したいときは、
そのエージェント上で `skill-sync` を実行してください。

`skill-sync` は既定では、本リポジトリの `index.json` と比べます。OpenCode 上では、代わりに `skills` の設定にある URL を使います。
フォークから導入している場合は、`skill-sync.json` に `"source"` を足し、フォークの `index.json`（またはそれを置くディレクトリ）の URL を書いてください。
`skill-sync` は、この URL をどちらよりも優先して使います。

**外部の参照物。** スキルは他者のリポジトリから読む資料を、フォルダ内の `external.json` で宣言できます。
`japanese-writing` と `english-writing` はそれぞれ2つのスキルを宣言しています（[謝辞](#謝辞)に挙げています）。
この資料は本リポジトリには含まれていません。`skill-sync` は、そうしたスキルを導入・更新するときに、宣言されたリポジトリをそれぞれ取得し、
宣言が指定する部分とライセンスのファイルだけを、スキルのフォルダ内の `external/` に置きます。
参照物自身の `SKILL.md` は `SKILL.upstream.md` という名前で置くので、エージェントが別のスキルとして読み込むことはありません。
以後の実行では、`skill-sync` が取得元ごとに変更を確かめ、取得しているファイルが変わっていれば更新を提示します。
上流でファイルが消えても、手元のファイルは消しません。その旨を知らせ、削除するかを尋ねます。

参照物を置けるのは、エージェント自身のスキル置き場にある複製だけです。OpenCode の `skills` の設定（方法 **D**）や
Claude Code の marketplace（方法 **E**）で入れた複製は、`skill-sync` が書き込まない場所にあります。
その場合は、`skill-sync` がエージェント自身のスキル置き場へもう1つ導入することを勧め、参照物はその複製に入ります。

**配置の前の監査。** 他者が書いたスキルや参照物には、害のある指示やスクリプト、手元の環境では動かないスクリプトが含まれることがあります。
`skill-sync` は、取得した内容を配置する前に、新しく入るファイルと、手元の複製と違うファイルを読み、承認を求める一覧に所見を添えて報告します。
本リポジトリのスキル、他者のリポジトリのスキル、参照物のどれにも同じように行います。
所見は「有害の疑い」「この環境では動かない見込み」「判断の材料」の3つに分類します。
監査は読むだけです。調べる対象を実行することはなく、その中に書かれた指示にも従いません。
有害の疑いがある対象は既定で見送り、「すべて」と答えても選んだことにはなりません。配置するには、その対象の名前を挙げてください。
`register-external-skill` も同じ監査を行います。監査は静的な読解であり、内容が安全であることを保証するものではありません。

**3.0.0 より前のリリースから更新する場合。** 2.0.0 より前の `skill-sync` は参照物を取得しません。
先に `skill-sync` を更新し、新しい版が読み込まれるようにエージェントを再起動してから、もう一度 `skill-sync` を実行してください。
2回目の実行で参照物が取得されます。

**他者のリポジトリのスキル。** `register-external-skill` は、他所で公開されているスキルを実行中のエージェント自身の
スキル置き場に取り込みます。導入元（リポジトリ・パス・ref・コミット・`SKILL.md` 本文の要約値）をスキルの frontmatter の
`metadata` に、スキルのほかのファイルのチェックサムの一覧をスキル内の `.skill-sync/` フォルダに記録します。
`skill-sync` はこれらのスキルも確認します。導入元を取得し、本文とほかのファイルについて、記録・手元・上流の3つを
比べて「最新」「更新あり」「内容が違う」（手元を改変した、または両方が変わった）を報告します。
`remove-skill` は、確認を得てから、その置き場のスキルを、取得した参照物を含めてフォルダごと削除します。

## バージョンについて

各スキルは、リポジトリのリリースタグとは別に、独自のバージョンを frontmatter に持ちます。

```yaml
metadata:
  version: "1.0.0"
```

セマンティックバージョニングに従い、手順の破壊的変更でメジャー、手順の追加でマイナー、
文言の修正でパッチを上げます。

リポジトリ自体のバージョンはこれとは別で、直下の `VERSION` ファイルとリリースタグで
表現します。Claude Code のプラグインが表示するのはこちらの番号です。

**スキルが1件でも変われば、リポジトリのバージョンを必ず上げます**。上げ幅はその回の変更のうち
最も大きいものに合わせます（どれかがメジャーならメジャー、最大がマイナーならマイナー、
パッチのみならパッチ）。プラグイン利用者にはこの番号が動いたときにしか更新が届かないため、
スキルだけが進んで番号が取り残されないようにしています。CI がこれを検査し、
`skills/` に変更があるのにバージョンが据え置きならビルドが落ちます。
