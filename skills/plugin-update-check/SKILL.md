# plugin-update-check: プラグイン更新の有無を調べる

> **skill version**: 1.1.0

セッション内で初めて本スキルを使用するときは「plugin-update-check スキル v1.1.0 を使用します」と宣言する。

npm プラグインは、OpenCode 本体の機構では自動で最新版に追随しない。本スキルは設定に書かれたプラグインについて、導入済みの版とレジストリの最新版を突き合わせ、更新の要否を一覧にするための手順書である。

本スキルは判定だけを行い、**適用はしない**。適用（キャッシュの削除と入れ直し）は `plugin-update-apply` の役目である。分けてあるのは、調べるだけの操作と、一時的にプラグインを使えなくする操作を混ぜないためである。

## 前提

- 設定ファイルは `~/.config/opencode/opencode.json` または `~/.config/opencode/opencode.jsonc`。どちらもありうるので、存在する方を読む。`XDG_CONFIG_HOME` で移動されていれば、移動先を見る。Windows では `~` をユーザープロファイル（`%USERPROFILE%`）に読み替える。
- プラグインのキャッシュの場所は、次の「キャッシュの場所」に従う。
- レジストリは `https://registry.npmjs.org/<パッケージ名>` で参照できる。

### キャッシュの場所

キャッシュの基点は `<XDG のキャッシュディレクトリ>/opencode` である。既定では `~/.cache/opencode` で、`XDG_CACHE_HOME` が設定されていれば `$XDG_CACHE_HOME/opencode` になる。Windows での基点は確認できていない。`~` をユーザープロファイル（`%USERPROFILE%`）に読み替えた場所をまず見て、無ければ探す。

npm のプラグインは基点の下の次の場所に置かれる。

```
<基点>/packages/<エントリ>/node_modules/<パッケージ名>/
```

`<エントリ>` は、設定の `plugin` 配列に書かれた文字列そのもの（をパスとして安全な形にしたもの）である。エントリが `<名前>` なら `<名前>`、`<名前>@latest` なら `<名前>@latest` のディレクトリになる。OpenCode が `@latest` を補うことはない。

同じパッケージについて `<名前>` と `<名前>@latest` のディレクトリが両方あるのは、設定のエントリの書き方を変えた後に古い方が残った場合である。読み込まれるのは現在の設定のエントリに対応するディレクトリで、もう一方は以前の設定の残りである。

手順のコマンドは、パスを既定の `~/.cache/opencode` で書いてある。`XDG_CACHE_HOME` で移動されている場合と Windows の場合は、コマンドのパスの `~/.cache/opencode` を実際の基点に読み替える。

## 手順

### 1. 設定からプラグインの一覧を取り出す

設定ファイルの `plugin` 配列を読む。各エントリの文字列は、版の指定（`@x.y.z`）が付いていても、**落とさず、そのまま記録する**。エントリの文字列は、キャッシュのディレクトリの名前にもなる。

エントリからパッケージ名を取り出すときは、先頭以外で最後の `@` より前を名前、後を版とする。先頭以外に `@` が無ければ、全体が名前である。スコープ付きの `@<スコープ>/<名前>@1.2.3` なら、名前は `@<スコープ>/<名前>`、版は `1.2.3` になる。

版の指定（`@x.y.z`）が付いたプラグインは、新しい版が出ていても意図して固定している可能性がある。以下ではこれを「版を固定しているプラグイン」と呼ぶ。`@latest` は版の固定ではない。

設定ファイルはコメントや末尾カンマを含むことがある。厳格な JSON パーサで読めなくても異常ではない。

### 2. レジストリの最新版を取得する

レジストリの API から直接取得する。この方法なら、node や npm が入っていない環境でも動く。

```bash
curl -sL "https://registry.npmjs.org/<パッケージ名>" | grep -o '"latest":"[^"]*"' | head -n1
```

`<パッケージ名>` には、手順1で版を除いて取り出した名前を使う。スコープ付きパッケージは、**`/` を `%2f` に置き換える**。`@<スコープ>/<名前>` なら `@<スコープ>%2f<名前>` と書く。スコープの無いパッケージはそのままでよい。

### 3. 導入済みの版を確認する

キャッシュの中の `package.json` を読む。`<エントリ>` は手順1で記録した文字列、`<パッケージ名>` は版を除いた名前である。

```bash
cat ~/.cache/opencode/packages/<エントリ>/node_modules/<パッケージ名>/package.json | grep '"version"'
```

その `version` の値が導入済みの版である。

参照先を間違えないこと。**実際に入っているものは `node_modules` の下にある**。キャッシュの直下にも `package.json` があるが、そちらは `{"dependencies": {...}}` の形で要求した版を書いたものであって、実体ではない。

スコープ付きパッケージのディレクトリは、エントリの文字列の `/` がパスとして安全な形にされるので、`@<スコープ>/<名前>/` の階層になるとは限らない(確認できていない)。`packages/` の下を見て実際の名前を確かめる。

`<名前>` と `<名前>@latest` のディレクトリが併存するときは、現在の設定のエントリに対応するディレクトリの版を導入済みの版とする。もう一方は読み込まれないので、手順4の表の備考に「以前の設定の残り」として示す。

### 4. 比較して報告する

表にまとめる。プラグインの列には版を除いた名前を書き、固定の版や以前の設定の残りは備考に書く。

| プラグイン | 導入済み | 最新 | 状態 | 備考 |
|---|---|---|---|---|
| （名前） | 1.0.0 | 1.0.0 | 最新 | |
| （名前） | 1.2.0 | 1.3.0 | **更新あり** | 以前の設定の残り: `（名前）@latest`（1.1.0） |
| （名前） | 2.0.0 | 2.1.0 | 版を固定 | 2.0.0 に固定 |

状態は次の5つのどれか1つを付ける。上から順に当てはまるかを見る。

| 状態 | 意味 |
|---|---|
| 見つからない | キャッシュかレジストリに見つからない。どちらに無かったかを備考に書く。 |
| 版を固定 | 版を固定しているプラグインである。最新版と違っていても更新対象にしない。 |
| 最新 | 導入済みの版と最新版が同じ。 |
| 更新あり | 最新版のほうが新しい。 |
| 導入済みのほうが新しい | 導入済みの版が、レジストリの `latest` の版より新しい。更新対象にしない。 |

見つからないものは、**エラーにせず、そのまま報告する**。設定に書いたばかりでまだ導入されていない場合や、パッケージ名が変わった場合がある。

版を固定しているプラグインは、最新版と違っていても**更新対象として扱わない**。固定を外すかどうかは利用者の判断であり、そのことを添えて知らせる。

「更新あり」が1件でもあれば、**再起動しただけでは更新されないことを併せて伝える**。npm プラグインは一度導入されるとキャッシュが固定されるため、キャッシュを消してからでないと新しい版が入らない。適用の手順は `plugin-update-apply` にある。
