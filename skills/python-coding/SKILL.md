# python-coding: Python コーディングの方針

> **skill version**: 1.2.0

セッション内で初めて本スキルを使用するときは「python-coding スキル v1.2.0 を使用します」と宣言する。

## 安全の規定

次の規定は安全に関わる。本文の各節に置いた規定のうち、これに当たるものをここに集める。

| 規定 | 本文の該当箇所 |
|---|---|
| 秘密情報(鍵・パスワード・トークン)をコードに直書きせず、環境変数や設定ファイルから読む。 | 設定値と秘密情報 |
| 秘密情報をログ・例外メッセージ・テストのフィクスチャに出さない。テストにはダミー値を使う。 | 設定値と秘密情報 |
| 外部コマンドは `subprocess.run` にリスト引数で渡し、シェルを経由しない。 | 標準ライブラリの慣用 |
| 不正な入力は入口で早く失敗させる。握りつぶして処理を続行しない。 | 例外の扱い |
| グローバルな Python 環境へパッケージをインストールしない。 | 検証の実行 |

**これらはプロジェクトの規約や既存コードの流儀より常に優先する**。規約が別のことを言っていても安全な書き方を採り、その旨を報告する。

## 方針の優先順位

「安全の規定」を除き、本スキルの規定は**既定**であり、プロジェクトの規約を上書きしない。次の順で決める。

1. プロジェクトに明記された規約。エージェント向けの指示書(`AGENTS.md` など)、貢献者向けの文書、lint・整形・型検査・テストの設定ファイル。
2. 既存コードの流儀。同じプロジェクトの既存コードとテストが採っている書き方。同じプロジェクトの中で流儀を混ぜない。
3. 本スキルの既定。以降の各節はこれにあたる。

1と2が矛盾すれば1に従う。

## 作業手順

1. 既存のプロジェクト規約、依存関係、テスト構成(テストの流儀とツールを含む)を確認する。確認した規約と流儀のどれに従うかの決め方は、「方針の優先順位」と「流儀の決め方」にある。ただし「安全の規定」は、規約と流儀より優先する。
2. 影響範囲を最小に保って実装または修正する。書き方の基準は、「実装基準」以降の各節にある。
3. 変更した Python ファイルを「検証の実行」に従って検証する。検証の範囲(構文確認、既存の lint・整形・型検査、テストが存在するならば全件の実行)と方法は、その節にまとめてある。

レビューを頼まれたときは、手順1と同じく規約と流儀を確かめたうえで、本スキルの規定に照らして指摘し、直すかどうかは依頼者に委ねる。

テストを先に書く進め方(テスト駆動開発)を採るかどうかは利用者の方針であり、本スキルは定めない。採る場合は、その進め方の手順に従う。

## 実装基準

- PEP 8 に従い、読みやすく一貫したコードを書く。
- クラスおよび公開関数・メソッドには PEP 257 に沿った docstring を書く。引数・戻り値・例外の書き方は「docstring の流儀」で決める。
- 引数・戻り値には、設計を明確にできる場合に PEP 484 準拠の型ヒントを付ける。意図的に多様な入力を許容する場合は、無理に不正確な型ヒントを付けない。
  - 対象の Python 版をプロジェクトの宣言(`requires-python`、`.python-version`、CI の設定)で確かめ、それより新しい構文を使わない。
  - 3.10 以上なら組み込み型と `|` の記法(`list[int]`、`X | None`)を使う。
  - `Any` は最後の手段とし、使うなら理由をコメントで添える。
- 意味のある構造には素の dict やタプルではなく dataclass・NamedTuple・Enum・TypedDict を使い、意図を型で示す。
- 単一責任を守り、機能単位で関数・クラス・モジュールを分割する。
- 1ファイルは原則1000行以内を目標にし、超える場合は責務で分割できないか検討する。
- 自明でない処理には、なぜその処理を行うかを説明する短いコメントを添える。docstring と同じ内容は繰り返さない。

### docstring の流儀

docstring の中の引数・戻り値・例外の書き方は、「方針の優先順位」を当てはめて次の順で決める。

1. プロジェクトに明記された流儀。
2. 既存コードの流儀。
3. Google 形式(`Args:`・`Returns:`・`Raises:` の節を立てる。本スキルの既定)。

どの流儀も PEP 257 の上に載る書き方であり、PEP 257 に沿うという規定は流儀によらず変わらない。一度決めた流儀を、同じプロジェクトの中で混ぜない。

## 例外の扱い

- 具体的な例外型を送出する。組み込みの例外で意味が合えばそれを使い、ライブラリやアプリケーションの境界では独自の例外を定義する。
- 捕捉する範囲は必要な例外型に絞る。裸の `except` や広すぎる捕捉を書かず、捕捉したら処理するか再送出する。
- 例外を捕捉して別の例外を送出するときは、原因を連鎖させる(`raise ... from e`)。
- 不正な入力は入口で早く失敗させる。握りつぶして処理を続行しない(「安全の規定」)。

## 標準ライブラリの慣用

- パス操作は `pathlib` を使う。
- 文字列の整形は f-string を使う。
- ファイルの読み書きは文字コードを明示する(`encoding="utf-8"` など)。
- ファイル・接続などのリソースは `with` で閉じる。
- 外部コマンドは `subprocess.run` にリスト引数で渡し、シェルを経由しない(「安全の規定」)。
- 可変な既定引数(list・dict など)を書かない。既定は `None` にして関数内で生成する。
- 診断出力は `logging` を使う。`print` は利用者に見せるための CLI の出力に限る。

## モジュール構成と import

- import はファイルの先頭にまとめ、標準ライブラリ→サードパーティ→自プロジェクトの順に並べ、絶対 import で書く。
- ワイルドカード import(`from x import *`)を書かない。
- 実行の入口は `if __name__ == "__main__":` のガードに置き、処理は関数にする。
- 循環 import を避ける。起きたら責務の分割で解消する。

## 設定値と秘密情報

- 環境依存の値(URL・パス・接続先)をコードに直書きせず、環境変数や設定ファイルから読む。
- 秘密情報(鍵・パスワード・トークン)は、コードへの直書きとログ・例外メッセージ・テストのフィクスチャへの出力を避ける。規定の内容は「安全の規定」にある。

## テストの書き方

### 流儀の決め方

「方針の優先順位」をテストに当てはめ、次の順で決める。

1. プロジェクトに明記された方針。書かれている場所は、エージェント向けの指示書、貢献者向けの文書、テストの設定ファイル、テスト用の依存関係の宣言、CI の設定である。テストの設定ファイルは、pytest なら `pytest.toml` / `pytest.ini` / `pyproject.toml` の pytest の節 / `tox.ini` / `setup.cfg` で、あれば従う。
2. 既存テストの流儀。テストディレクトリの中身を見て、unittest 流か pytest 流か、配置と命名を確かめる。流儀が混在していれば、テストの実行手段(ランナー)が前提とする流儀に合わせる。判別できなければ利用者に確認する。
3. pytest 準拠(本スキルの既定)。

一度決めた流儀を、同じプロジェクトの中で混ぜない。

### pytest 準拠で書くときの規定

1. 探索規則に合う命名にする。ファイルは `test_*.py`、関数は `test_` で始める。クラスにまとめるなら `Test` で始め、`__init__` を持たせない。
2. 配置は既存の配置に従う。無ければ `tests/` をパッケージの外に置き、対象モジュールの構成を写す。
3. 検証は素の `assert` で書く。unittest 流の assert メソッドは使わない。何と何を比べたかが失敗時に読めるようにし、自明でなければメッセージを添える。
4. 例外の検証は `pytest.raises` で行い、メッセージの照合(`match`)を添える。
5. 同じ形のケースが並ぶなら `pytest.mark.parametrize` にまとめ、ケースごとに識別できる名前を付ける(`ids`)。
6. 準備と後始末は fixture で行う。組み込みの `tmp_path`(テストごとの一時ディレクトリ)・`monkeypatch`(属性・環境変数の一時変更)・`capsys`(標準出力の捕捉)を自作より優先する。
7. 複数のファイルで共有する fixture は `conftest.py` に置く。
8. `unittest.TestCase` を混ぜない。pytest でも実行はできるが、fixture の引数注入とパラメータ化が使えず、流儀が割れる。
9. 各テストは独立させ、決定的にする。他のテストの実行順や結果に依存しない。ネットワーク・現在時刻・乱数・作業ディレクトリへの書き込みに依存しない。一時領域は `tmp_path` を使う。
10. スキップ・期待失敗のマーカーは理由付きでのみ使う。テストの設定ファイルを新設せず、要るなら提案して確認を得る。

### テストの実行

- プロジェクトの実行手段で**全件**を実行し、通過・失敗・スキップの件数を報告する。pytest 準拠なら、実行手段の既定は `python -m pytest` である。対象を絞った実行だけで「通った」としない。

## 検証の実行

変更後の検証は、変更した Python ファイルの構文確認、既存の lint・整形・型検査、テストが存在するならば全件の実行、を範囲とする。テストの実行手段と件数の報告は「テストの実行」に従う。

- 構文確認は py_compile ではなく linter(ruff など)に任せる。linter が無く、追加も断られたときは、`python -m py_compile`(複数なら `python -m compileall`)で構文だけを確かめ、linter が無いことを報告する。
- 決定論的に行える検証はツールで行い、LLM エージェントは行わない。検証が失敗したときだけ、出力の要点の抽出を解析専任サブエージェントに委譲する。委譲できない環境では自分で解析する。原因の分析と修正方針は、呼び出し元モデルが行う。
- 既存の lint・整形・型検査の設定と、環境の実行手段(仮想環境・ランナー)をそのまま使う。
- 新しいツール・依存関係・設定ファイルを勝手に足さない。要るなら候補と理由を挙げて確認を得る。
- グローバルな Python 環境へパッケージをインストールしない(「安全の規定」)。
