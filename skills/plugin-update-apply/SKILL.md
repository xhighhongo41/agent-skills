# plugin-update-apply: プラグイン更新を適用する

> **skill version**: 1.1.0

セッション内で初めて本スキルを使用するときは「plugin-update-apply スキル v1.1.0 を使用します」と宣言する。

npm プラグインは一度導入されるとキャッシュが固定され、再起動しただけでは新しい版に入れ替わらない。本スキルはキャッシュを削除し、再起動によって最新版を入れ直すための手順書である。

本スキルは適用だけを担う。更新の要否を判定するのは `plugin-update-check` の役目である。

## 承認の徹底（最優先の制約）

- キャッシュの削除自体は取り返しのつく操作だが、再起動するまでそのプラグインが使えなくなることがある。
- したがって、削除を実行する前に、対象のプラグイン名と削除する理由を示し、**明示的な承認を得る**。示す項目の一覧は手順2にある。**承認が無いうちは、ファイルシステムに一切手を加えてはならない**。
- **曖昧な返事を承認とみなさない**。「うーん」「まあ」のような返答は保留として扱い、もう一度確認する。実行してよいと読み取れる返答があったときにだけ次へ進む。

## 前提

キャッシュの配置は次のとおりである。削除するディレクトリはこの配置から決まる。

### キャッシュの場所

キャッシュの基点は `<XDG のキャッシュディレクトリ>/opencode` である。既定では `~/.cache/opencode` で、`XDG_CACHE_HOME` が設定されていれば `$XDG_CACHE_HOME/opencode` になる。Windows での基点は確認できていない。`~` をユーザープロファイル（`%USERPROFILE%`）に読み替えた場所をまず見て、無ければ探す。

npm のプラグインは基点の下の次の場所に置かれる。

```
<基点>/packages/<エントリ>/node_modules/<パッケージ名>/
```

`<エントリ>` は、設定の `plugin` 配列に書かれた文字列そのもの（をパスとして安全な形にしたもの）である。エントリが `<名前>` なら `<名前>`、`<名前>@latest` なら `<名前>@latest` のディレクトリになる。OpenCode が `@latest` を補うことはない。

同じパッケージについて `<名前>` と `<名前>@latest` のディレクトリが両方あるのは、設定のエントリの書き方を変えた後に古い方が残った場合である。読み込まれるのは現在の設定のエントリに対応するディレクトリで、もう一方は以前の設定の残りである。

手順のコマンドは、パスを既定の `~/.cache/opencode` で書いてある。`XDG_CACHE_HOME` で移動されている場合と Windows の場合は、コマンドのパスの `~/.cache/opencode` を実際の基点に読み替える。

## 手順

### 1. 対象を特定する

`plugin-update-check` の結果、または新たに確認した更新対象を挙げる。対象ごとに、設定の `plugin` 配列に書かれたエントリの文字列をそのまま控える。削除するディレクトリの名前になる。

版の指定（`@x.y.z`）が付いたプラグインを、以下では「版を固定しているプラグイン」と呼ぶ。版を固定しているプラグインは、**更新対象にしない**。固定を外すかどうかは利用者の判断であり、勝手に最新版へ動かしてよいものではない。

### 2. 承認を求める

何がどうなるのかが分かる形で示してから尋ねる。示すのは、プラグイン名・削除する理由・導入済みの版・最新版・削除するディレクトリである。

削除するのは、現在の設定のエントリに対応するディレクトリである。読み込まれるのはこのディレクトリなので、これを消せば次回の起動で入れ直される。

```
~/.cache/opencode/packages/<エントリ>
```

`<エントリ>` は手順1で控えた文字列で、`<名前>` か `<名前>@latest` のどちらかである。もう一方のディレクトリも残っていれば、それは以前の設定の残りであり、読み込まれない。一緒に消してもよいが、消すなら以前の設定の残りであることを示して承認の対象に含める。

スコープ付きパッケージのディレクトリは、エントリの文字列の `/` がパスとして安全な形にされるので、`@<スコープ>/<名前>` の階層になるとは限らない(確認できていない)。`packages/` の下を見て実際の名前を確かめる。**消す前にパスの実在を確かめる**。

返事の扱いは「承認の徹底」に従う。

### 3. 削除する

承認が得られたら実行する。承認は手順2で1度得れば足りるが、**1件消すごとに結果を確かめてから次へ進む**。1件は1つのディレクトリを指す。まとめて実行してから最後に確認する、という進め方はしない。

```bash
rm -rf ~/.cache/opencode/packages/<エントリ>
```

以前の設定の残りも消すことが承認されていれば、同じ形で別の1件として消す。

削除に失敗したら、1件目であってもそこで止め、残りへ進まない。どこまで消したかを「うまくいかないときの確認」の「途中で失敗した」に従って報告する。

**承認された対象の外へ広げない**。ワイルドカードでまとめて消すことはしない。

### 4. 削除できたことを確認する

消したディレクトリごとに確かめる。`<名前>` と `<名前>@latest` の両方を消したなら、両方について実行する。

```bash
ls -d ~/.cache/opencode/packages/<消したディレクトリ> 2>/dev/null
```

何も出力されなければ、削除できている。`2>/dev/null` を付けるのは、消えていること自体が期待どおりの結果であり、そのときのエラー出力に意味が無いためである。

### 5. 再起動を依頼する

キャッシュが消えたので、次回の起動時に最新版が導入される。**再起動は利用者が行う**。都合のよいタイミングで再起動してもらうよう伝える。

### 6. 再起動後に確認する（任意）

再起動が済んだら、入った版を確かめる。`<パッケージ名>` は、エントリから版の指定を除いた名前である。

```bash
cat ~/.cache/opencode/packages/<エントリ>/node_modules/<パッケージ名>/package.json | grep '"version"'
```

`version` が期待した版になっていれば、適用できている。**参照するのは `node_modules` の下**である。キャッシュの直下の `package.json` は要求した版を書いたものであって、実体ではない。

## うまくいかないときの確認

- 再起動しても版が変わらない: 消したのが現在の設定のエントリに対応するディレクトリかを確認する。以前の設定の残りだけを消しても、読み込まれるディレクトリは入れ替わらない。
- プラグインが読み込まれなくなった: 設定に書かれた名前が正しいか、レジストリからそのパッケージを取得できるかを確認する。ネットワークにつながらない状態で再起動すると、消したまま入れ直せないことがある。
- 途中で失敗した: **どこまで消したかを必ず報告する**。中途半端に消えた状態を隠さない。
