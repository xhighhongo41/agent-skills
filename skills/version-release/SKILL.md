# version-release: バージョンリリースの定型手順

> **skill version**: 1.5.0

セッション内で初めて本スキルを使用するときは「version-release スキル v1.5.0 を使用します」と宣言する。

実装と検証が完了した版を、作業ブランチから既定ブランチへマージし、タグを付けるところまで確実に届けるためのゲート式のチェックリストである。既定ブランチ(`main` など)はリポジトリの実際の既定ブランチを使う。
各ゲートは順番に実行し、確認の結果を必ずユーザーに見える形で出力する。ゲートが失敗したら**先へ進まず**、修正してコミットしたうえで、そのゲートから再実行する。

## 前提と一般化ルール

- 完了要件の達成と**ユーザーの最終承認**が済んでいること。最終承認は、ユーザーが本スキルを起動したことをもって得たものとみなす。ただし、実装記録に未解決の中断論点が残っていれば承認の前提が欠けているので、このスキルを進めず、論点を示して停止する。達成の証拠と中断論点の有無はG0で照合する。
- 対象プロジェクトの言語・エコシステムを前提にしない。バージョン宣言ファイルも、ホスティングサービスも、派生公開先も、探索と慣行の読み取りで特定する。
- 進行文書はプロジェクトのコンセプトと各版の計画概要を記載した文書である。名称と形式はプロジェクトによって異なる。
- ホスティングサービスがGitHubでないプロジェクトや、リモートが無いプロジェクトでは、PRとリリース文書のゲート(G6のPRの作成、G8)を相当する手段に読み替えるか、スキップする。タグの付与(G7)と、G9・G10は行う。どう読み替えたかを報告する。
- リリース文書の公開は行わず、**ドラフトまで**とする。公開ボタンはユーザーが押す。タグのpushや既定ブランチへのマージで自動的に始まる公開(G2で「自動」と判定したもの)は、本スキルの操作の結果として起こることをG2の表で示したうえで行う。force pushと履歴の改変は使わない。
- ユーザーに選択肢を提示するときは、何を決めるのか、各選択肢を採るとどうなるか、推奨案とその理由を、計画書もコードも精読していない読み手が判断できる日本語で書く。ファイル名・ブランチ名・コマンドは補足に留める。コードを読まないと答えられない問いは、それ自体が進行のボトルネックになるからである。

## 版の状態の見分け方

> この節は version-start / version-implement / version-release の3スキルが同じ文で持つ。直すときは3つを同時に直す。

各スキルの入口の手順は、指定された版がいまどの段階にあるかを本節の①〜③で決め、要約を表示してから進む。

### ① 状態の表

表は後ろの状態(リリース済み)から並べてある。判定は**上から順に当て、最初に当てはまった状態を採る**。リリース済みの版はブランチも計画書も持つので、未着手の側から当てると誤る。

| 状態 | 意味 | 見分ける証拠 |
|---|---|---|
| リリース済み | リリースが完了 | タグがあり、作業ブランチが既定ブランチにマージ済み。進行文書の当該版の記載がリリース済みを示す |
| リリース中 | リリース(version-release 相当)が途中 | PR・既定ブランチへのマージ・タグ・リリース文書・進行文書のリリース済みの記載のうち、一部だけがある |
| 実装完了 | 実装が完了し、リリース待ち | 実装記録に完了要件の全数照合と申し送りがあり、進行文書の当該版の記載が実装完了を示す。タグが無く、既定ブランチに未マージ |
| 実装中 | 実装(version-implement 相当)が途中 | 計画書が「確定」になっている、または実装記録がある。実装記録に完了要件の全数照合が無いか、照合はあるが進行文書の当該版の記載が実装完了を示さない(version-implement の G3 の途中で止まった)。タグが無い |
| 設計済み | 設計が完了し、計画は確定待ち | 作業ブランチ・計画書(ドラフト)・進行文書の当該版の記載(設計)があり、実装記録が無い |
| 設計中 | 設計(version-start 相当)が途中で止まっている | 作業ブランチと計画書のどちらか一方だけがある。または計画書はあるが、直近版の計画書にある節が欠けている。または両方あるが、進行文書に当該版の記載が無い |
| 未着手 | 誰も手を付けていない | 作業ブランチ・計画書・実装記録・タグのいずれも無い |

### ② 証拠の在処

名前や置き場は決め打ちせず、進行文書と既存の配置・慣行から特定する。

| 証拠 | 見る場所 | 注意 |
|---|---|---|
| 作業ブランチ | ローカルとリモートの両方のブランチ一覧。命名慣行は既存ブランチから読む | リモートにだけあって計画書が手元に無いときは、別マシンで設計中・設計済みの可能性がある(計画書が git 非追跡のプロジェクトで起こる) |
| タグ | タグ一覧(リモートから取得してから見る)。命名慣行は既存タグから読む。**直近リリース版**は、タグを版番号順に並べた最大 | 取得できなければローカルのタグで判定し、その旨を要約に書く |
| マージ状況 | 作業ブランチの先端が既定ブランチに含まれ、かつ作業ブランチに自分のコミット(既定ブランチの本流、つまりマージコミットの1番目の親だけをたどった履歴に無いコミット)があるか | 自分のコミットが無い作業ブランチ(作った直後のもの)は、先端が既定ブランチに含まれても未マージとして扱う。早送り(fast-forward)・squash・rebase でマージする慣行のプロジェクトでは、この見方ではマージ済みに見えないので、タグと進行文書の記載(version-release はPRの状態も)で判定する。既定ブランチはリポジトリの実際のものを使う |
| PR・リリース文書 | ホスティングサービスの CLI で照会する。照会するのは version-release だけ(version-start / version-implement は git の証拠で足りる) | 照会できなければ「未確認」と書く。推測で埋めない。CLI のアカウント確認の規定に従う |
| 計画書 | 実装計画の置き場(進行文書の参照と既存の配置から特定)。存在、前付けの状態(ドラフト/確定)、直近版の計画書と比べた節の欠け | 直近版が無い初版は、version-start が定める標準構成と比べる |
| 実装記録 | 同じ置き場。存在、進捗管理の表、完了要件の照合の節、申し送りの節、未解決の中断論点 | |
| 進行文書 | 当該版の記載(状態〈設計/実装完了/リリース済み〉と日付、要点。旧形式の版ごとのエントリも記載として読む)、次版への要望の反映済みの印、ロードマップ | **進行文書が次に予定している版**はここから読む(未反映の要望、ロードマップの次の版) |
| 版宣言ファイル | version-release の G1 が探索するもの(例: `VERSION`)。現在値が直近リリース版と一致するか | 補助。食い違えば要約に書く |

### ③ 要約の形

要約は期待どおりでも**必ず表示する**。

- リポジトリ(名前と場所)と進行文書の表題。別プロジェクトの版番号を打っていないかを目に入れるため
- 直近リリース版(タグ)
- 進行文書が次に予定している版
- 着手済みで未リリースの版(ブランチまたは計画書があってタグが無いもの)
- 指定された版と、①で決めた状態とその根拠
- 判定: **一致**(このスキルが期待する状態)か、食い違いの種類(下の「食い違いの語彙」)

### 食い違いの語彙

版 A.B の「後継」は A.(B+1) または (A+1).0 である。引数は `X.Y.Z` でも `X.Y` でも受け、ブランチ名とタグ名は慣行に従って読み替える。

| 語 | 定義 |
|---|---|
| 飛び越し | 指定版より小さい版に、リリースされていないものがある(着手済みで未リリース、または進行文書が予定していて未着手) |
| 不在 | 指定版が進行文書のどこにも無く、直近リリース版の後継でも、着手済みで未リリースの版の後継でもない。別プロジェクトの版番号の疑い |
| 後退 | 指定版が直近リリース版より小さい。タグがあればリリース済みの扱い、無ければ不在の扱い |
| 前工程が未了 | 指定版の状態が、このスキルが期待する状態より前 |
| 後工程に進んでいる | 指定版の状態が、このスキルが期待する状態より後 |
| 自スキルの途中 | 指定版の状態が、このスキル自身の「途中」(設計中/実装中/リリース中)。再開の対象 |

### 判定の順

①で指定版の状態を決め、不在(状態が未着手のときだけ起こる)と飛び越しに当たるかを確かめる。そのうえで、スキルごとの入口の表を上から順に当て、最初に当てはまった行を採る。不在と飛び越しの行も、表の中の位置で当てる。不在と飛び越しが同時なら、不在を優先する(別プロジェクトの疑いの方が重い)。不在と飛び越しは、行に当たらなくても要約に書く。

### 選択肢の出し方

食い違いのときは、何が食い違っているか、各選択肢を採るとどうなるか、推奨案とその理由を、計画書もコードも精読していない読み手が判断できる日本語で書く。ブランチ名・ファイル名・コマンドは括弧書きに留める。選択肢を示して回答を得られる対話手段があればそれを使い、無ければ通常の対話で尋ねる。**得た方針でそのまま継続する**(回答を待って中断する形にしない)。「停止」を選ばれたら、要約と次に使う手順を報告して止まる。

期待どおりのときは**確認を取らず**、要約の表示だけで進む。自スキルの途中も期待どおりとして扱い、選択肢を出さずに要約を表示して再開する(再開の手順の中で各スキルが定める確認、たとえば未コミット変更の扱いは行う)。ただし、作業ブランチがリモートにだけあって手元に計画書が無いとき(別マシンで進めた可能性)は、選択肢を出す。

## 申し送りの扱い

> この節は version-start / version-implement / version-release の3スキルが同じ文で持つ。直すときは3つを同時に直す。

**申し送りとは**将来の版で行動を要する事項である。環境の事実・教訓・観察の記録は申し送りにせず、実装記録に残す。申し送りを必要以上に重く扱わないために、まず「事実」を申し送りから外す。

### 3段階

表の上から順に当て、最初に当たった段階を採る。どれにも当たらなければ Optional とする。

| 段階 | 定義 |
|---|---|
| Critical | 近い将来の版で対応が必須のもの。意図的に先送りして実装が存在しない部分、明らかなセキュリティホール、致命的なバグ、依存ライブラリ・外部サービスの仕様変更による動作不能(の予告) |
| Recommended | 実装することがプロジェクトの自然な次の版になるもの。大きな性能改善、利用者体験の明確な向上 |
| Optional | それ以外。完全性は上がるが前2者ほどの重大性は無いもの |

### 申し送り文書

内部資料置き場(実装計画・実装記録と同じ置き場)に1つ置く。名前は進行文書や既存のファイルに別名があればそれ、無ければ `エージェント申し送り事項.md` とする。文書が無ければ、最初に必要としたスキルが作る。

形式は段階ごとの表と、末尾の「消去した項目」である。

- 段階ごとの表の列: ID／発生版／要旨／実装すると何が変わるか／望ましい実装／考えられる影響／状態〈未着手・採用(vX.Y)・実装済み(vX.Y)・保留〉
- 「消去した項目」に書くもの: ID／消去日／理由

ID は `H` に通し番号を付け、消去しても再利用しない。

### 消去の規則

version-start と version-release は申し送り文書を見直し、obsolete になった項目(実装済み・対象消失・ユーザーが恒久的に対応しないと指示したもの)を本文から消して、「消去した項目」に1行残す。消去はユーザーに確認してから行う。

### 採用の規則

進行文書の要望欄(ユーザー記載)が最上位であり、申し送りはそれを補う参考に過ぎない。

version-start は **Critical だけ**を対象に、「本版で対応するか」をまとめて1回尋ねる。Critical が無ければ尋ねず、その旨を報告する。Recommended と Optional は件数と要旨の一覧を示すだけにする。採用を勧めず、計画に勝手に入れない。ユーザーが選んだものだけを入れる。

採用が決まった項目は、version-start が状態列を「採用(vX.Y)」にする。実装が終わった項目は、version-implement の G3 が状態列を「実装済み(vX.Y)」にする。消去は version-release の G10 が、消去の規則に従って行う(理由は実装済み)。

### 進行文書の記載

版ごとの記載は進行文書の1か所に集約する。形は履歴の表の1行など、進行文書の既存の形に従う。各フェーズ(設計・実装完了・リリース)は追記せずにその1か所を**更新**する。更新するのは状態と日付、要点で、合計の目安は200字である。詳細は計画書と実装記録に書く。**ユーザー記載は消さない**。

進行文書に次版への要望の欄(ユーザー記載)があれば、version-start は計画書へ反映した時点で、その版の要望の見出しに反映済みの印(日付と状態)を付ける。以降のフェーズ(実装完了・リリース)は、版ごとの記載と同じく、その印の状態を更新する。要望の本文は変えない。

旧形式(版ごとに設計／実装完了／リリースのエントリを足す形)が既にある進行文書では、既存の版は旧形式のまま読み、新しい版から集約する。旧形式のエントリしか無い版(移行期)は、そのエントリを当該版の記載として更新するか、新しい形へ写してから更新する。

## プロジェクト毎スクリプトの利用(推奨)

決定論的に判定できるゲート(G1のバージョン照合、G4の検証、G5のクリーン確認)は、**プロジェクト毎のリリース前チェックスクリプト**(例: `tools/release_check.sh <version>`)にまとめるのが望ましい。G0のgit側の証拠収集(ブランチ・タグ・マージ状況)も含めてよい。

- スクリプトが既にあるプロジェクトでは、G1の冒頭でそれを実行し(G0のgit側の証拠集めに使ってもよい)、該当するゲートの手動の手順の代わりにその結果を報告する。G1〜G3で修正をコミットしたときは、G4でもう一度実行する。スクリプトが検証一括スクリプトを内包していれば、G4で検証一括スクリプトを改めて実行しなくてよい。内包していなければ、G4で検証一括スクリプトも実行する。
- 無いプロジェクトで本スキルを初めて実行したときは、G5の最後に、今回の探索結果を固定したチェックスクリプトを作ることをユーザーに提案する(G5から参照する)。以後の版ではチェックが機械的な保証になる。

## ホスティングサービスのCLIとアカウントの確認

PRの作成やリリースドラフトの作成には、ホスティングサービスのCLI(GitHubなら`gh`)を使うことが多い。この種のCLIは複数のアカウントを同時に保持し、そのうち1つをアクティブにする構成を取れる。アクティブなアカウントがリモートの所有者と異なると、操作が権限エラーで失敗する。作業の途中で失敗すると復旧が煩雑なので、最初にCLIを使うゲート(通常はG0)に入る**前に**確認する。確認と承認はリリース全体で1回とし、CLIを使うゲート(G0・G6・G7・G8など)ごとには取り直さない。

1. リモートの所有者を読む(`git remote -v`など)。
2. CLIが保持しているアカウントと、どれがアクティブかを確認する(GitHubなら`gh auth status`)。
3. アクティブなアカウントがリモートの所有者と異なる場合は、そのままでは失敗する。CLIの設定はリポジトリの外にあるため、**切り替えの承認をユーザーに求める**。
   このとき手順を停止しない。その場でユーザーに方針を尋ね、得た方針でそのまま進行を継続する。選択肢を提示できる質問手段があれば、それを使う。「回答を待って中断する」形にはしない。
4. 承認が得られたら、アクティブなアカウントを一時的に切り替える(GitHubなら`gh auth switch`)。承認が得られなければ、CLIを使うゲートを実施せず、何が未了かを明示して報告する。
5. CLIを使うゲートを順に行う。
6. 最後にCLIを使うゲート(通常はG8のドラフト作成。G8を行わないときは、それまでに最後にCLIを使ったゲート)の直後に、**必ず元のアクティブなアカウントへ戻す**。作業が失敗した場合も、中断した場合も戻す。戻す操作に承認は要らない。元の状態に戻すだけだからである。
7. 戻したことを完了報告に明記する。

なお、リモートのURLがSSHのホストエイリアスなどで解決される構成では、`git push`自体はCLIのアクティブなアカウントに影響されない。一方、HTTPSとCLIの認証ヘルパを使う構成では、`git push`も影響を受ける。どちらの構成かを先に決めず、実際にエラーが出た操作を手がかりに判断する。

## ゲート

### G0: 入場ゲート — 版の状態照合と再開判定

1. PRとリリース文書の照会にCLIを使うので、着手前に「ホスティングサービスのCLIとアカウントの確認」を実施する。そのうえで、「版の状態の見分け方」の表を引いて証拠を集め、要約を表示する。照会できなければ「未確認」と書き、推測で埋めない。本スキルが期待する状態は実装完了(再開ならリリース中)である。
2. 判定は次の表を上から順に当てる。ただし、実装記録に未解決の中断論点が残っていれば、表のどの行でも進まずに停止し、論点を示す(前提の「最終承認」)。

| 判定 | 扱い | 選択肢 |
|---|---|---|
| 未着手・設計中(未設計) | **停止**。version-start を案内する。不在のときもこの行に当たるので、別プロジェクトの版番号の疑いを要約に書く | 出さない |
| 設計済み・実装中(未実装) | **停止**。何が欠けているか(計画書の確定/実装記録の完了要件照合/進行文書の当該版の記載〈実装完了〉)を列挙し、version-implement(の完了ゲート)を案内する。ユーザーが完了を明言する場合も、実装記録の完了要件照合を済ませてから再実行するよう伝える | 出さない |
| リリース済み | **停止**。タグ・マージコミット・PR・リリース文書を示し、追加の変更は次の版(パッチを含む)としてversion-startから始めることを案内する | 出さない |
| 飛び越し(下位に着手済みで未リリースの版がある) | 情報を提示して尋ねる | (a) 停止して確認(推奨) (b) 指定版で続行(リリース順が入れ替わることの帰結を要約に書く: 「最新リリース」の印の付き方、後から出す下位版の版番号の扱い) |
| リリース中(自スキルの途中) | 3の再開判定へ。期待どおりとして扱い、選択肢は出さない | — |
| 一致(実装完了) | 進む。確認は取らない | — |

3. **再開判定**(リリース中のとき)。済んだと判定できるのは、リポジトリの外か既定ブランチに痕跡が残るゲートだけである。**G1〜G5は常に再実行する**(安価で冪等なため)。マージ済みなら、G1〜G5は既定ブランチ上で見る。G9も常に実行する。

| 証拠 | 意味 | 再開位置 |
|---|---|---|
| PRがある(未マージ) | G6の途中 | CIの確認とマージから(PRは作り直さない) |
| 作業ブランチが既定ブランチにマージ済み | G6完了 | マージコミットを特定してG7へ(既定ブランチへのマージを起点とする派生公開先があれば、起動確認だけは行う) |
| タグがローカルにだけある | G7の途中 | タグのpushから(付け直さない) |
| タグがリモートにもある | G7完了 | G8へ(タグ起点の派生公開先があれば起動確認だけは行う) |
| リリース文書がある(ドラフトまたは公開) | G8完了 | G9・G10へ(ドラフトを作り直さない) |
| 実装記録にリリースの節がある(進行文書の記載は未更新) | G10の途中 | G10の3(進行文書の更新)から。申し送りの消去と実装記録の節はやり直さない |
| 進行文書の当該版の記載がリリース済みを示す | G10完了 | 完了報告へ |

再開の表(ゲート/証拠/済・未)を出力してから、最初の未済ゲートへ進む。**済んだゲートをやり直さない**。タグの付け直し、PRの作り直し、リリース文書の二重作成をしない。リリース文書が無いことはG8が未済であることを意味するが、スキップするかどうかはG8の規定で決める。前回`--no-release`を付けていたなら、再実行でも付ける。

4. G0の結果も他のゲートと同じくユーザーに見える形で出力する。

### G1: バージョン宣言の探索と照合(上げ忘れ検出の核心)

特定のファイルに絞らず、バージョンを宣言しているファイルをリポジトリ全体から探索する。探索の観点は次のとおり。

- マニフェスト類: `pyproject.toml` / `package.json` / `Cargo.toml` / `*.gemspec` / `*.csproj` / `CMakeLists.txt` / `VERSION` / `Makefile` など、そのエコシステムでバージョンを持つファイル
- コード内宣言: `__version__` / `version =` / `VERSION =` などのgrep
- 文書内表記: README(多言語版を含む)の版の表記・変更履歴、ステータス表記

リリース前チェックスクリプトがあれば、先に実行する(「プロジェクト毎スクリプトの利用」)。見つかった全宣言を「ファイル:行 → 現在値 → 目標版との整合」の表で表示し、照合する。dev サフィックスの扱いなどの慣行は進行文書・実装記録・既存タグから読む。タグの時点で`X.Y.0.dev0`を維持する慣行のプロジェクトもあるので、前版の実績に合わせる。不一致は修正し、コミットしてから次へ進む。

### G2: 派生公開先の追随確認

タグとリリース文書はリポジトリの中で完結するが、利用者が実際に取りに行く場所はその外にあることが多い。パッケージレジストリ、コンテナレジストリ、静的ホスティング、URLで直接取得されるマニフェスト、文書サイトなど、**リポジトリから派生してリポジトリの外で公開・配備されるもの**(派生公開先)が本版で最新になるかを、マージ前に確かめる。タグとリリース文書そのものはここに含めない。タグはG7、リリース文書はG8が扱う。

1. 派生公開先を探索する。下の表の手がかりを上から順に当たり、当てはまるものを全部拾う。表は手がかりの種別を示すもので、例示したファイル名・サービス名に限らない。

| 手がかり | 見るもの | 分かること |
|---|---|---|
| CI/CDの公開ジョブ | ワークフロー定義にある publish / deploy / upload / push 相当のステップと、その起動条件(タグpush・リリース公開・既定ブランチへのpush・手動) | 自動更新の有無と起動条件 |
| デプロイ設定ファイル | 静的ホスティング・コンテナ・PaaSの設定(例: `wrangler.toml` / `netlify.toml` / `vercel.json` / `fly.toml` / `Dockerfile` / compose / Helm chart) | 公開先の種別と、設定内に直書きされた版 |
| パッケージのメタデータ | `pyproject.toml` / `package.json` / `Cargo.toml` / gemspec などの公開用メタデータ(レジストリ名・非公開の印・長い説明文の出どころ) | レジストリ公開の有無と、公開文書がREADMEから流れるか |
| 文書サイトの設定 | mkdocs / Docusaurus / Sphinx などの設定、Pages用ブランチ | 文書サイトの有無と、版の表記の出どころ |
| URLで配られるマニフェスト | 利用者がURLで直接取得するファイル(index / marketplace / formula / プラグインのmanifestなど) | 既定ブランチへのマージで即時に反映される公開物 |
| READMEのバッジ・導入コマンド | バッジのURL、`pip install` / `docker pull` / `npm i` / `brew` などの導入コマンド | 利用者が取りに行く公開先の名前 |
| 進行文書・前版の記録 | 配布経路の記載、前版のリリース記録にある公開後の確認 | 探索の見落とし防止 |

2. 見つかった派生公開先を表にして表示する。列は「公開先 / 種別 / 更新の起動条件 / 版の出どころ(ファイル:行 またはタグ) / 本版で最新になるか(自動・要修正・手動・未確認) / 必要な作業」とする。派生公開先が無ければ、「派生公開先なし」と明記して pass とする。
3. 1件ずつ判定する。上から順に当てはまるものを採る。
   - **自動**: 起動条件が本リリースの操作(タグpush・リリース公開・既定ブランチへのマージ)であり、公開される版がG1で照合済みの宣言から取られる → pass。派生公開先がコミット済みの生成物なら、再生成済みで宣言と一致していることまで見る。起動条件の種類を控えておく(G7・G8・完了報告で使う)。タグ名の規則(例: `v*`)と本版のタグ名が合うことも見る。
   - **要修正**: 派生公開先の設定に版が直書きされていて古い、または派生公開先へ流れる公開文書に古い版の表記がある → 直してコミットし、本ゲートを再実行する(G1と同じ扱い)。
   - **手動**: 公開ジョブが無い、または起動条件が手動しか無い → 手順とコマンドを完了報告の「ユーザーに残る作業」に書く。公開ジョブを新設することは本スキルの範囲外で、提案に留める。
   - **未確認**: 外部サービス側の状態を確認できない → 「未確認」と書く。推測で埋めない(実在しない「更新あり」を並べない)。

要修正の分岐がコミットを伴うため、本ゲートはマージ(G6)より前に置いている。

### G3: 文書の追随確認

- README(と多言語版)が本版の内容に追随しているか、古くなった記述(古い手順・古い版の表記)が残っていないかを確認する。変更履歴があれば、本版のエントリを確認する。
- 実装記録(またはそれに相当する文書)が完成しているかを確認する。

### G4: 検証ゲート

- プロジェクトの検証一括スクリプト(例: `tools/check.sh`)を実行し、すべてpassすることを確かめる。G1で実行したリリース前チェックスクリプトがそれを内包していれば、その結果で足りる。無ければ、lintとテストに相当するコマンドを実行する。
- 失敗した場合は原因を解析し(必要なら解析専任のサブエージェントへ委譲する)、修正して再実行する。**テスト側を弱めて通すことは禁止する**。

### G5: クリーン確認

- `git status`で未コミットの変更が無いことを確かめる(進行文書などgit非追跡のものは除く)。
- ブランチの全コミットがリモートへpush済みであることを確かめる。
- リリース前チェックスクリプトが無ければ、ここでその作成を提案する(「プロジェクト毎スクリプトの利用」)。

### G6: PR作成とマージ

- 着手前に「ホスティングサービスのCLIとアカウントの確認」を実施する(未実施なら先にそちらを行う)。
- 作業ブランチから既定ブランチへのPRを作成する。本文は「Summary(変更の要点)+Verification(検証結果の実測値)」の構成とし、プロジェクトの言語方針(OSSなら英語)に従う。
- CIがあれば、**CIが成功したことを確認してから**マージする。マージ方式(merge commit / squash / rebase)は`git log`にある過去のマージの慣行に合わせる。
- 既定ブランチへのマージを起動条件とする派生公開先(G2で「自動」と判定したもの)があれば、マージの後に自動公開のジョブが起動したかを1回確認する。扱いはG7のタグpushの場合と同じである(完了を待ち続けない。失敗していれば先へ進まずユーザーに報告する)。

### G7: タグ付与

- タグの命名は既存タグの慣行に合わせる(例: `vX.Y.0`)。**注釈付きタグをマージコミットに付与**し、pushする。
- タグpushを起動条件とする派生公開先(G2で「自動」と判定したもの)があれば、push後に自動公開のジョブが起動したかを1回確認する(GitHubなら`gh run list`など)。完了を待ち続けない。起動の有無と直近の状態を報告する。失敗していれば、**先へ進まずユーザーに報告する**。このとき、タグの削除やロールバックはしない。

### G8: リリースノート(該当する場合のみ)

- `--no-release`を指定されたとき、またはリリースに値しない版(内部整理だけの版、プライベートリポジトリの場合など)は、スキップする。判断に迷う場合はユーザーに確認する。
- 作成する場合は、前版までのリリースノートのスタイルと言語を踏襲し、ドラフトとして作成する(GitHubなら`gh release create --draft`)。公開はユーザーが行う旨を報告に明記する。
- リリース公開を起動条件とする派生公開先(G2)があれば、「公開後に○○が動くので確認してほしい」という案内を報告に含める。

### G9: ローカルブランチとリモートブランチの同期確認

- ローカルブランチ(特に既定ブランチ)がリモートと同期されているかを確認する。マージ後もローカルの既定ブランチは古いまま残りやすいので、明示的に確認する。
- ローカルブランチが古い場合は、リモートから同期し、最新の状態になったことを確認する。

### G10: 進行文書への完了記載

再開判定は進行文書の記載でG10の完了を見るので、進行文書の更新を最後に行う。

1. 申し送り文書を見直す(「申し送りの扱い」の節に従う)。本版で「実装済み(vX.Y)」になった項目など、obsolete になった項目を、ユーザーに確認してから消去して「消去した項目」に残す。リリース時に判明した「行動を要する」事項を段階付きで追加する。環境の事実は実装記録に書く。
2. 実装記録にリリースの節を足す。書くのはPR番号・マージコミット・タグ・リリースドラフトの有無、派生公開先の最終状態(G2の表)、次の版の予定である。
3. 最後に、進行文書の当該版の記載を更新する(「申し送りの扱い」の「進行文書の記載」に従う)。書くのは状態=リリース済み、日付、タグ、PRである。要点は必要なら整える。次版への要望の欄の反映済みの印も、状態をリリース済みに更新する。**エージェント記載であることと日付を明示**する。

## 完了報告

次の項目を整理して報告する。

- 全ゲートの結果(pass/修正内容)
- PR・タグ・リリースドラフトのURL
- 派生公開先ごとの最終状態(自動で済んだもの・公開後に動くもの・手作業が要るもの)
- ユーザーに残る作業(リリース公開、手動の派生公開)
- 申し送り文書への変更(消去・追加した ID)

アカウントを一時的に切り替えた場合は、元へ戻したことを明記する。再開したときは、飛ばしたゲートとその根拠を明記する。
