# version-start: バージョン開発開始の定型手順

> **skill version**: 1.0.0

セッション内で初めて本スキルを使用するときは「version-start スキル v1.0.0 を使用します」と宣言する。

新しいバージョンの「設計」フェーズを、コンテキストゼロの状態から実装計画確定直前まで進めるための手順書。**このスキルの完了地点は「実装計画書のドラフト完成+要確認事項の提示」であり、実装には絶対に入らない**。実装開始はユーザーの明示指示を待つ。

## 前提と一般化ルール

- 対象プロジェクトの言語・技術スタック・文書規約は**ハードコードしない**。すべてPROJECT.mdと既存文書・既存コードから発見する。
- PROJECT.mdがリポジトリ直下に無い場合は手順を進めず、プロジェクトの進行文書の所在をユーザーに確認する。
- 開発資料フォルダ(実装計画・実装記録の置き場)の名前はプロジェクト毎に異なる。PROJECT.md内の参照から特定する。
- 各文書のフォーマット・言語(日本語/英語)は、**同プロジェクトの直近バージョンの同種文書を雛形として踏襲**する。初バージョンで前例が無い場合のみ本スキル末尾の標準構成を使う。

## 手順

### 1. 版番号とスコープの特定

- 引数の版番号を採用。引数が無ければPROJECT.mdから「次はvX.Y」を特定し、ユーザーに確認してから進む。
- PROJECT.mdの当該版スコープ(ロードマップ文書があればその該当節も)と、**前版の完了エントリ**を読み、この版で「やること/やらないこと(スコープ外)」の輪郭を掴む。

### 2. 文書読解 — 読解手段は内容に応じて選択する

読むべき文書: PROJECT.md全体 / ロードマップの該当節 / 直近1〜2版の実装記録(特に申し送り節) / 関連する事前調査資料。

読解手段は**メインセッションが文書ごとに選択**する。判断基準:

| 手段 | 使いどころ |
|---|---|
| メインセッション自身が読む | 設計判断に直結する骨幹文書(PROJECT.md、ロードマップ該当節、直近版の申し送り)。全文のニュアンスが計画品質を左右するもの |
| 上位の読解役サブエージェントへ委譲 | 内容の高度な把握・構造化要約が必要な長文資料(過去版の実装計画・実装記録の全体、長い事前調査資料) |
| 軽量な読解役サブエージェントへ委譲 | 機械的な抽出・検索で足りるもの(特定節の抜き出し、キーワード該当箇所の収集、ファイル構成の列挙) |

委譲する場合は自己完結したプロンプト(対象パス・抽出してほしい観点・出典付き報告の指示)で、独立したものは**並列**に投げる(エージェントの同時実行制約の範囲内で)。委譲結果は鵜呑みにせず、計画に直結する事実は必要に応じて原典を確認する。

### 3. コードベース把握

- この版で触ることになる「接ぎ木点」(変更対象のモジュール、拡張ポイント、既存のインターフェース、設定・CLI・テストの構造)を調査する。手段の選択基準は手順2と同じ(コード調査は読解役・探索役サブエージェントへの並列委譲が基本、設計判断に直結する核心部はメインが読む)。
- 外部仕様の事実確認(ライブラリのバージョン制約、APIの挙動など)が必要ならWeb調査役サブエージェントへ委譲する。**まずローカルのコード・設定・ドキュメントを確認し、不明点は推測せず「仮定」として明記**する(調査ルール)。

### 4. ブランチ作成

- 作業ツリーがクリーンであることを確認する(未コミット変更があればユーザーに確認)。
- プロジェクトのブランチ命名慣行を`git branch -a`と過去の記録から読み(例: `v0.7`)、**当該版のブランチが無ければ作成**する。リモートがあればpushする。

### 5. 実装計画書の作成

開発資料フォルダに「vX.Y実装計画.md」を作成する。**直近版の実装計画のフォーマットを踏襲**すること。前例が無い場合の標準構成:

1. 前付け(作成日・作成者・状態=**ドラフト、ユーザーレビュー待ち**・参照資料・新規調査の一覧)
2. **§0 ユーザー確認事項**(回答を得て計画を確定させる論点。推奨案と根拠を添え、番号を振る)
3. 目的と完了要件(R1..Rn。**検証可能な形**で書く)/ スコープ外(やらないこと)
4. 確定済みの前提(実装担当者が疑わなくてよい事実。出典付き)
5. 成果物一覧(ファイルツリー差分)
6. 技術設計(節分け。テスト戦略=TDD3段階の適用方針を含む)
7. リスクと対処の決定木(C1..Cn。実装担当者が上から順に試せる形)
8. タスク分割(T1..Tn+任意タスク。委譲先サブエージェントの役割案と依存関係)
9. 進行ルール(サイクル・コミット単位・コミットメッセージ言語)
10. 次工程への出力(この版が後続版に渡すもの)

計画書の品質要件:

- 完了要件には**検証コマンドを明記**する。lint+テストの検証一括スクリプト(例: `tools/check.sh`)がプロジェクトにあればそれを指定し、**無ければ「検証一括スクリプトの作成」を本版のタスクに含める**ことを提案する(決定論的チェックはスクリプト化してエージェント間で共有するのが方針)。
- リスク決定木(C1..Cn)は**実装中に起こりうる分岐を可能な限り網羅**する。後続のversion-implementは「決定木にある問題は自走、ない問題は中断してユーザー確認」で動くため、決定木の網羅性がそのまま実装の自律性を決める。
- 下位モデルへの委譲を想定し、タスクは「対象パス・確定済み設計・完了要件・確認コマンド」を明記できる粒度で切る。ただしコードそのものは書かない。

### 6. PROJECT.mdへの追記と提示

- PROJECT.mdに設計フェーズのエントリを追記する(**エージェント記載であることと日付を明示**、ドラフト状態と§0の項目数を明記。ユーザー記載部分は削除しない)。
- ユーザーへの報告では、計画の骨子と**§0の確認事項を読みやすく提示**し、回答を求めて**停止**する。「実装はレビューと§0確定後、ユーザーの開始指示を待って着手する」と明記する。
