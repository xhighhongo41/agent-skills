# project-start: 新規プロジェクト開始の定型手順

> **skill version**: 1.0.0

セッション内で初めて本スキルを使用するときは「project-start スキル v1.0.0 を使用します」と宣言する。

新しいプロジェクトのディレクトリを、**リモートとアカウント・コミット識別子・進行文書の骨格・ライセンス・`.gitignore`・プロジェクト固有指示ファイル・初回コミットと push** まで整えるための手順書である。
誤ったアカウントでコミットや push をしてしまう事故、進行文書が肥大する問題、プロジェクトごとに構成が揺れる問題を、着手の時点で防ぐ。

**4つの原則**

1. **再入可能にする。** 各手順は「現状を調べる → 不足だけを行う → 状態表を更新する」の形を取る。完了後や中断後に再実行しても、整っているものには触らない。
2. **確認は4か所に限る。** ①`git init`（手順1） ②ファイルの作成・変更は手順0の表の直後に「行うこと」を列挙して**まとめて1回**（手順3〜7の書き込みはすべてこの1回に含める。以降は尋ね直さない） ③コミット（手順8。対象を示す） ④**リモートへ出る操作**（リモートの作成・push）は**その都度個別に**。アカウントの切り替えも承認を要する。
3. **尋ねることはまとめる。** 利用者の判断が要る事項（既定ブランチ名、リモートの扱い、識別子、ファイル名、ライセンス、言語）は手順0の表の直後に一度に尋ねる（選択肢を示して回答を得られる対話手段があればそれを使う）。手順の途中で1つずつ往復しない。
4. **エージェント固有の知識は表に隔離する。** 固有指示ファイルの名前、CLI の名前は末尾の表で引く。手順本体は表に無いエージェントにも通用する形で書く。

## 前提と一般化ルール

- **実行中のエージェントを判別し**、固有指示ファイルの名前を「エージェントとファイル名」の表で引く。判別できなければ利用者に尋ねる。
- ホスティングサービスは GitHub を例に書く。CLI は表の列で引き、他のサービスではその CLI に読み替える。CLI が無ければ、所有者・アカウントは利用者に尋ねる。
- **リモートには「所有者を持つもの」と「持たないもの」がある。** ホスティングサービス上のリポジトリは所有者（利用者または組織）を持つ。ローカルのベアリポジトリ、`file://`、自前のホストなど URL から所有者を読めないものは「所有者なし」として扱い、アカウントの照合を省く（識別子は利用者の確認だけ）。
- 固有指示ファイルに書く言語は、利用者のグローバル指示書（`CLAUDE.md` / `AGENTS.md` 相当）と同じにする。無ければ尋ねる。
- 既定ブランチ名は、リモートがあれば**リモートの HEAD**（`git symbolic-ref refs/remotes/origin/HEAD` または `git remote show origin`）、新規に初期化するなら `git config init.defaultBranch`、どちらも無ければ `main` を既定案にして尋ねる。
- 「進行根幹ファイル」（プロジェクトの方針と版ごとの要約を置く文書）と「内部資料置き場」（版ごとの計画・記録・申し送りを置く、git 非追跡のフォルダ）の名前は**決め打ちしない**。プロジェクトごとに違う（手順4）。
- 引数は不要。

## 手順

### 0. 現状の把握（状態表）と確認

次の項目を**一度に調べ**、表（項目／現状／判定／根拠／対応する手順）にして示す。判定は「整っている」「要対応」「未判定」の3つ。git リポジトリの外では項目2・4・10 は「未判定」とする。

| # | 項目 | 調べ方 | 「整っている」の条件 | 手順 |
|---|---|---|---|---|
| 1 | git リポジトリ | リポジトリの中かどうか（`git rev-parse --is-inside-work-tree`） | リポジトリである | 1 |
| 2 | リモートと所有者 | `git remote -v` の URL から host / owner / repo を読む | リモートがあり所有者が読める。または「所有者なし」「ローカル完結」と固有指示ファイルに記録済み | 1 |
| 3 | CLI のアカウント | CLI のアカウント一覧（GitHub なら `gh auth status`。各アカウントに `Active account: true/false` が出る） | CLI が所有者のアカウントを**保持している**（アクティブかどうかは問わない。リモートへ出る操作のときだけ切り替える）。または所有者なし・ローカル完結 | 2 |
| 4 | コミット識別子 | `git config --local user.name` / `user.email`（無ければ効いている値を `git config user.name` 等で） | 所有者（または利用者が決めたアカウント）に対応する値がローカル設定にあり、OS のログイン名が混じっていない（アカウント名と同じ場合を除く） | 3 |
| 5 | 進行根幹ファイル | 手順4の探索 | 存在し、固有指示ファイルに記載がある | 4 |
| 6 | 内部資料置き場 | 手順4の探索 | 存在し、固有指示ファイルに記載がある | 4 |
| 7 | ライセンス | `LICENSE` / `LICENSE.md` / `COPYING` | 存在する。または「無し」と固有指示ファイルに記録済み | 5 |
| 8 | `.gitignore` | ファイルの有無と既定3項目（根幹ファイル・内部資料置き場・固有指示ファイル） | 存在し、既定3項目（固有指示ファイルに例外の記録があればそれに従う）を含む | 6 |
| 9 | 固有指示ファイル | 表の名前のファイルと、本スキルの節の印（手順7） | 節があり、内容が項目2〜8と一致 | 7 |
| 10 | 未コミット・未 push | `git status`、上流があれば未 push のコミット | どちらも無い | 8 |

**すべて「整っている」なら「作業不要」と報告して終わる。** そうでなければ、

1. 利用者の判断が要る事項（原則3）を**一度に尋ねる**。表で「要対応」「未判定」になった項目に関わるものだけでよい。
2. 答えを得たら「行うこと」（作る・変えるファイルと、その内容の要点）を列挙し、**まとめて1回確認する**（原則2の②）。
3. 該当する手順だけを 1 → 8 の順に行い、整っている手順は飛ばす。

### 1. リポジトリの由来とリモート

由来を3つに分ける。

- **(a) 非 git**: `git init` を提案して承認を得る（原則2の①）。既定ブランチ名は「前提」のとおり。初期化後は (c) へ。
- **(b) リモートあり**: URL から host / owner / repo を読む。`git@host:owner/repo.git` と `https://host/owner/repo(.git)` の両形式を読む。
  SSH のホストエイリアス（`git@github-xxx:owner/repo.git` のような形）では owner / repo だけが確実なので、host は利用者に確認する。
  ローカルのパス・`file://`・自前のホストなど所有者を読めない URL は「所有者なし」とし、手順7で記録する。
- **(c) git あり・リモート無し**: 手順0で尋ねた答えに従う。
  - **リモートを作る** → 可視性（private を既定案）、名前（ディレクトリ名を既定案）、作成に使うアカウントを決め、手順2を先に通してから、**個別に確認を取って**作る（原則2の④）。
    GitHub なら `gh repo create <owner>/<name> --source . --remote origin --private`（または `--public`）。push は手順8で行う。
    **`--source` はライセンスや `.gitignore` のテンプレート指定と併用できない**ので、それらは手順5・6でローカルに作る。
  - **既存のリモートを設定する**（別ホスト・ローカルのベアリポジトリなど）→ `git remote add origin <URL>` を行い、以後は (b) として扱う。
  - **ローカル完結** → 手順7で「ローカル完結」と記録する。手順2の照合は省き、手順3は利用者が使う名前とメールの確認だけにする。

### 2. アカウントの照合

所有者を持つリモート（手順1）のときだけ行う。ホスティング CLI は**複数のアカウントを保持し、そのうち1つがアクティブ**という構成を取れる。アクティブが所有者と違うと、リモートの作成や push が権限エラーで落ちる。

1. CLI のアカウント一覧とアクティブを読む（GitHub なら `gh auth status`）。
2. **所有者のアカウントを保持している**なら、それを「このプロジェクトで使うアカウント」にする。アクティブでなくてもここでは切り替えない。**リモートへ出る操作（手順1(c) の作成、手順8の push）の直前に承認を得て切り替え、操作が終わったら成否にかかわらず必ず元へ戻す**（戻す操作に承認は要らない。手順9で戻したことを報告する）。承認が得られなければ、その操作を行わず、未了として報告する。
3. **保持していない**（利用者がコラボレータとして別のアカウントで操作する等）なら、利用者が指定するアカウントを「使うアカウント」にする。権限の有無は実際のリモート操作で分かる（落ちたら報告する）。
4. 所有者が組織（GitHub なら `gh api users/<owner> --jq .type` が `Organization`）なら、使うアカウントがその組織で操作できるかを CLI で確認できる範囲で確かめる（`gh repo view <owner>/<repo> --json viewerPermission` など）。確認できなければ「未確認」と書き、利用者に確認する。
5. 決めたアカウントを状態表に残す（手順7で固有指示ファイルに書く値になる）。

CLI が無い、または GitHub 以外でアカウントを読めない場合は、使うアカウントを利用者に尋ねる。推測で埋めない。

### 3. コミット識別子

ローカル設定の `user.name` / `user.email` を読む（未設定なら、グローバル設定から効いている値を「現在効いている値」として示す）。次の順で照合する。

1. **名前**が手順2のアカウント名、または利用者が認めた表示名か。
2. **メール**がそのアカウントに紐づくものか。GitHub では noreply 形式 `<id>+<login>@users.noreply.github.com` を**既定案**にする（`id` は `gh api users/<login> --jq .id` で読める。アクティブなアカウントに依存しない。2017年7月より前のアカウントは `<login>@users.noreply.github.com` のこともある）。GitHub 以外では利用者に尋ねる。利用者が別のメールを使うなら、それを認める。
3. 名前またはメールに **OS のログイン名**（`whoami` 相当）が混じっていないか。混じっていれば警告する（アカウント名と同じ場合を除く）。

不一致・未設定なら、手順0で得た答えに従って **`git config --local user.name` / `user.email` に書く**（原則2の②に含まれる）。グローバル設定は変えない。所有者なし・ローカル完結なら、利用者が使う名前とメールを確認して書く。

### 4. 進行根幹ファイルと内部資料置き場

次の順で探し、**①②で明らかなら確認せずに採用する**。

1. 利用者のグローバル指示書に名前が書かれていればそれ（例: 進行根幹ファイルの名前、内部資料のフォルダ名）。
2. 既存の固有指示ファイルに書かれていればそれ。
3. ディレクトリ内の候補（進行・計画・ロードマップの語を持つ Markdown、資料・docs の名を持つフォルダ）。候補があれば手順0で確認する。

無ければ、名前の既定案を**利用者の言語と慣行に合わせて**提案し、手順0で尋ねる（名前を決め打ちしない）。作成は、進行根幹ファイル1つ（表題と「この文書の役割」の数行、要望欄の見出し）と、内部資料置き場のフォルダ1つ（空）。

### 5. ライセンス

`LICENSE` / `LICENSE.md` / `COPYING` を探す。**あればそれに従い**、名前を状態表に記す（手順7で固有指示ファイルに書く）。
無ければ、手順0で尋ねた答え（MIT / Apache-2.0 / GPL-3.0 / 非公開のため無し / その他。相談があれば、公開の有無・派生物への条件・特許条項の要否を聞いて支援する）に従う。

本文は**テンプレートから取得する**（記憶から書かない）。GitHub では `gh repo license view <key>`（例: `mit`）、無ければ `gh api /licenses/<key> --jq .body`。どちらも使えなければ、本文の入手を利用者に頼むか、ライセンス無しで進めて後で足す。
年と権利者（アカウント名を既定案にして手順0で尋ねる）を埋めて `LICENSE` に置く。

### 6. `.gitignore`

プロジェクトの言語は手順0で尋ねる（既存のファイルから推定できれば確認だけ）。テンプレートは `gh repo gitignore view <Name>`（名前は大文字小文字を区別する。例: `Python`）、無ければ `gh api /gitignore/templates/<Name> --jq .source`。どちらも使えなければ、その言語の標準的な生成物だけを利用者と相談して書く。

- 既存の `.gitignore` があれば**末尾に追記**する（テンプレートの行のうち無いものと、下の既定3項目。既にある行は重複して書かない）。
- **既定で、進行根幹ファイル・内部資料置き場・固有指示ファイルを加える**（git 非追跡にする）。利用者が明示的に例外を指示した場合（例: 固有指示ファイルは追跡する）はそれに従い、手順7で例外を記録する。
- **既に git で追跡されているファイルは、ignore に書いても効かない。** その旨を報告し、追跡を外すかは利用者に委ねる（勝手に追跡を外さない）。

### 7. プロジェクト固有指示ファイル

「エージェントとファイル名」の表から名前を引く。手順2〜6で決まった値（アカウント・識別子・根幹ファイル・置き場・ライセンス・ignore の例外）をここで書くので、この手順は手順6の後に置いてある。

- **無ければ**、下の「固有指示ファイルに書く節の雛形」から作る。
- **あれば**、本スキルの節の印（見出し `## プロジェクト構成（project-start が管理）` と、その直下の `<!-- project-start: managed -->` の行）を探す。
  - 印が無ければ、節を**末尾に追記**する。**既存の文は書き換えない。**
  - 印があれば、現在値との差分を示して節の中だけを書き換える（差分の確認は原則2の②の1回に含める）。
- **固有指示ファイルが git で追跡されている**（他の人と共有するリポジトリ等）なら、アカウント名とメールの値は書かず「使用アカウントと識別子は各自の手元設定に従う」と書く。個人の識別子を他人のリポジトリへ push しない。
- 他のエージェント向けのファイル（表の他の行）は、**同内容で作ることを提案するだけ**にする。利用者が望めば作る。

### 8. コミットと push

1. 対象ファイルを列挙して確認を取り（原則2の③）、コミットする。コミットメッセージの言語は、固有指示ファイル → グローバル指示書 → 利用者に尋ねる、の順で決める。
2. リモートがあれば、**既定ブランチへの push を個別に確認してから**行う（原則2の④。`git push -u origin <既定ブランチ>`。ブランチ名を明示し、`--all` や `--mirror` は使わない）。ローカル完結なら push を省く。
3. 使うアカウントがアクティブでなければ、push の直前に承認を得て切り替え（手順2）、push の後に戻す。
4. push が権限エラーで落ちたら、アクティブなアカウントの不一致を疑い、手順2の規定で切り替えてから push をやり直す。それでも落ちれば未了として報告する。

### 9. 完了報告

最終の状態表（全項目が「整っている」）、作成・変更したファイル、リモートの URL、使うアカウント、残る作業（リモート側の設定、追跡を外すかの判断など）を報告する。アカウントを切り替えていたら、戻したことを明記する。

## 再実行と中断からの再開

各手順が「調べてから不足だけ行う」形なので、**再実行は常に手順0から始めればよい**。再開専用の分岐は無い。
途中で止まった中間状態（例: `git init` 済みでリモート未作成、ファイルは作ったが未コミット）は、状態表の「要対応」として自然に拾われる。
全項目が整っていれば「作業不要」で終わる。これが再入可能であることの判定条件である。アカウントの切り替えは操作の間だけなので、戻した後に再実行しても項目3は「整っている」のままになる。

### 固有指示ファイルに書く節の雛形

見出しと印は固定し、各項目の値を埋める。言語は「前提」のとおり。

```
## プロジェクト構成（project-start が管理）
<!-- project-start: managed -->

1. リモートリポジトリ: <host>/<owner>/<repo>（所有者なしの URL、またはローカル完結）。既定ブランチ: <名前>。
2. 使用アカウント: <login>。コミット識別子: user.name=<値> / user.email=<値>。
   （このファイルを git で追跡する場合は「各自の手元設定に従う」とだけ書く）
3. 禁止事項: この PC の OS のログイン名や、上記以外のアカウントでコミット・push しない。
   ホスティング CLI を使う前にアクティブなアカウントを確認し、違えば切り替えて作業後に戻す。
4. 進行根幹ファイル: <path>（git 非追跡）。内部資料置き場: <dir>/（git 非追跡）。
   版ごとの実装計画・実装記録・申し送り文書はここに置く。追跡の例外: <無し／固有指示ファイルは追跡 など>。
5. 根幹ファイルの扱い: ユーザー記載を許可なく消さない。版ごとの詳細は内部資料置き場の計画・記録に書き、
   根幹ファイルには版ごとに目安200字のサマリだけを残す。
6. ライセンス: <名前>（LICENSE ファイル）、または「無し」。
```

## うまくいかないときの確認

- **リモートの URL から所有者が読めない**: SSH のホストエイリアスなら owner / repo を利用者に確認する。ローカルのパスや自前のホストなら「所有者なし」として進める。
- **CLI が無い／ログインしていない**: アカウントの照合は利用者への確認に置き換える。`gh auth login` の案内は利用者が自分で行う操作として示す。
- **CLI が認証エラー（401）を返す**: トークンの期限切れ。再ログインを案内する。
- **リモートの作成で「既に存在する」**: 同名のリポジトリがある。別名にするか、既存をリモートに設定する（手順1(c) の2つ目）。
- **固有指示ファイルの節が二重にある**: 手で足した痕跡。どちらを残すか利用者に確認し、片方を消す（確認なしに消さない）。
- **`.gitignore` に根幹ファイルが別表記で既にある**: 重複を足さない。既存の行が効いていることを `git check-ignore` で確かめる。
- **再実行のたびにアカウントの切り替えを求められる**: 項目3の条件は「保持している」であり「アクティブである」ではない。切り替えを求めるのはリモートへ出る操作の直前だけである。
