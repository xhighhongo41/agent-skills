# project-start: 新規プロジェクト開始の定型手順

> **skill version**: 1.0.0

セッション内で初めて本スキルを使用するときは「project-start スキル v1.0.0 を使用します」と宣言する。

新しいプロジェクトのディレクトリを、**リモートとアカウント・コミット識別子・進行文書の骨格・プロジェクト固有指示ファイル・ライセンス・`.gitignore`・初回コミットと push** まで整えるための手順書である。
誤ったアカウントでコミットや push をしてしまう事故、進行文書が肥大する問題、プロジェクトごとに構成が揺れる問題を、着手の時点で防ぐ。

**3つの原則**

1. **再入可能にする。** 各手順は「現状を調べる → 不足だけを行う → 状態表を更新する」の形を取る。完了後や中断後に再実行しても、整っているものには触らない。
2. **書く前に確認する。** ファイルの作成・変更はまとめて1回確認を取る。**リポジトリの外へ出る操作（リモートの作成・push）はその都度、個別に確認する。**
3. **エージェント固有の知識は表に隔離する。** 固有指示ファイルの名前、CLI の名前は末尾の表で引く。手順本体は表に無いエージェントにも通用する形で書く。

## 前提と一般化ルール

- **実行中のエージェントを判別し**、固有指示ファイルの名前を「エージェントとファイル名」の表で引く。判別できなければ利用者に尋ねる。
- ホスティングサービスは GitHub を例に書く。CLI は表の列で引き、他のサービスではその CLI に読み替える。CLI が無ければ、所有者・アカウントは利用者に尋ねる。
- 固有指示ファイルに書く言語は、利用者のグローバル指示書（`CLAUDE.md` / `AGENTS.md` 相当）と同じにする。無ければ尋ねる。
- 既定ブランチ名は `git config init.defaultBranch` の値。無ければ `main` を既定案にして尋ねる。
- 「進行根幹ファイル」（プロジェクトの方針と版ごとの要約を置く文書）と「内部資料置き場」（版ごとの計画・記録・申し送りを置く、git 非追跡のフォルダ）の名前は**決め打ちしない**。プロジェクトごとに違う（手順4）。
- 引数は不要。

## 手順

### 0. 現状の把握（状態表）

次の項目を**一度に調べ**、表（項目／現状／判定／根拠）にして示す。判定は「整っている」「要対応」「未判定」の3つ。

| # | 項目 | 調べ方 | 「整っている」の条件 |
|---|---|---|---|
| 1 | git リポジトリ | リポジトリの中かどうか（`git rev-parse --is-inside-work-tree`） | リポジトリである |
| 2 | リモートと所有者 | `git remote -v` の URL から host / owner / repo を読む | リモートがあり所有者が読める。または「ローカル完結」と固有指示ファイルに記録済み |
| 3 | CLI のアカウント | CLI のアカウント一覧とアクティブ（GitHub なら `gh auth status`） | アクティブなアカウントが所有者と一致。またはローカル完結 |
| 4 | コミット識別子 | `git config --local user.name` / `user.email`（無ければ効いている値を `git config user.name` 等で） | 所有者に対応する値がローカル設定にあり、OS のログイン名が混じっていない |
| 5 | 進行根幹ファイル | 手順4の探索 | 存在し、固有指示ファイルに記載がある |
| 6 | 内部資料置き場 | 手順4の探索 | 存在し、固有指示ファイルに記載がある |
| 7 | 固有指示ファイル | 表の名前のファイルと、本スキルの節の印（手順5） | 節があり、内容が項目2〜6・8と一致 |
| 8 | ライセンス | `LICENSE` / `LICENSE.md` / `COPYING` | 存在する。または「無し」と固有指示ファイルに記録済み |
| 9 | `.gitignore` | ファイルの有無と既定3項目（根幹ファイル・内部資料置き場・固有指示ファイル） | 存在し、既定3項目（利用者の例外指示があればそれ）を含む |
| 10 | 未コミット・未 push | `git status`、上流があれば未 push のコミット | どちらも無い |

**すべて「整っている」なら「作業不要」と報告して終わる。** 1つでも「要対応」「未判定」があれば、該当する手順だけを 1 → 8 の順に行い、整っている手順は飛ばす。

### 1. リポジトリの由来とリモート

由来を3つに分ける。

- **(a) 非 git**: `git init` を提案する（既定ブランチ名は「前提」のとおり）。承認後に初期化し、(c) へ。
- **(b) リモートあり（クローンまたはリモート設定済み）**: URL から host / owner / repo を読む。`git@host:owner/repo.git` と `https://host/owner/repo(.git)` の両形式を読む。
  SSH のホストエイリアス（`git@github-xxx:owner/repo.git` のような形）では owner / repo だけが確実なので、host は利用者に確認する。
- **(c) git あり・リモート無し**: 利用者に尋ねる。
  - **リモートを作る** → 可視性（private を既定案）、名前（ディレクトリ名を既定案）、作成に使うアカウントを決め、**手順2のアカウント確認を先に通してから**作る。
    GitHub なら `gh repo create <owner>/<name> --source . --remote origin --private`（または `--public`）。push は手順8で行う。
    **`--source` はライセンスや `.gitignore` のテンプレート指定と併用できない**ので、それらは手順6・7でローカルに作る。
  - **ローカル完結** → 固有指示ファイルに「ローカル完結」と記す。手順2・3の所有者照合は、利用者が使う名前とメールの確認だけにする。

### 2. アカウントの照合

ホスティング CLI は**複数のアカウントを保持し、そのうち1つがアクティブ**という構成を取れる。アクティブが所有者と違うと、リモートの作成や push が権限エラーで落ちる。

1. リモートの所有者（手順1）を読む。
2. CLI のアカウント一覧とアクティブを読む（GitHub なら `gh auth status`。各アカウントに `Active account: true/false` が出る）。
3. **アクティブが所有者と一致**ならそのまま。**違えば**、切り替えの承認を利用者に求める（手順は止めず、その場で方針を尋ねて続ける）。承認後に `gh auth switch --user <所有者>` で一時的に切り替え、**本スキルの作業が終わったら必ず元へ戻す**（成否にかかわらず。戻す操作に承認は要らない）。
4. 所有者が組織のときは、利用者のアカウントがその組織で操作できるかを CLI で確認できる範囲で確かめる（`gh repo view --json viewerPermission` など）。確認できなければ「未確認」と書き、利用者に確認する。
5. **このプロジェクトで使うアカウントを1つ決め**、状態表に残す（手順5で固有指示ファイルに書く値になる）。

CLI が無い、または GitHub 以外でアカウントを読めない場合は、所有者とアカウントを利用者に尋ねる。推測で埋めない。

### 3. コミット識別子

ローカル設定の `user.name` / `user.email` を読む（未設定なら、グローバル設定から効いている値を「現在効いている値」として示す）。次の順で照合する。

1. **名前**が手順2のアカウント名、または利用者が認めた表示名か。
2. **メール**がそのアカウントに紐づくものか。GitHub では noreply 形式 `<id>+<login>@users.noreply.github.com` を**既定案**にする（`id` と `login` は `gh api user` で読める。2017年7月より前のアカウントは `<login>@users.noreply.github.com` のこともある）。利用者が別のメールを使うなら、それを認める。
3. 名前またはメールに **OS のログイン名**（`whoami` 相当）が混じっていないか。混じっていれば警告する（アカウント名と同じ場合を除く）。

不一致・未設定なら、利用者に確認して **`git config --local user.name` / `user.email` に書く**。グローバル設定は変えない。

### 4. 進行根幹ファイルと内部資料置き場

次の順で探し、**①②で明らかなら確認せずに採用する**。

1. 利用者のグローバル指示書に名前が書かれていればそれ（例: 進行根幹ファイルの名前、内部資料のフォルダ名）。
2. 既存の固有指示ファイルに書かれていればそれ。
3. ディレクトリ内の候補（進行・計画・ロードマップの語を持つ Markdown、資料・docs の名を持つフォルダ）。候補があれば利用者に確認する。

無ければ、名前の既定案を**利用者の言語と慣行に合わせて**提案し、尋ねる（名前を決め打ちしない）。作成は、進行根幹ファイル1つ（表題と「この文書の役割」の数行、要望欄の見出し）と、内部資料置き場のフォルダ1つ（空）。

### 5. プロジェクト固有指示ファイル

「エージェントとファイル名」の表から名前を引く。

- **無ければ**、下の「固有指示ファイルに書く節の雛形」から作る。
- **あれば**、本スキルの節の印（見出し `## プロジェクト構成（project-start が管理）` と、その直下の `<!-- project-start: managed -->` の行）を探す。
  - 印が無ければ、節を**末尾に追記**する。**既存の文は書き換えない。**
  - 印があれば、現在値との差分を示し、更新の確認を取ってから節の中だけを書き換える。
- 他のエージェント向けのファイル（表の他の行）は、**同内容で作ることを提案するだけ**にする。利用者が望めば作る。

### 6. ライセンス

`LICENSE` / `LICENSE.md` / `COPYING` を探す。**あればそれに従い**、名前を状態表と固有指示ファイルに記す。
無ければ、選択肢（MIT / Apache-2.0 / GPL-3.0 / 非公開のため無し / その他）を示して決めてもらう。相談があれば、公開の有無・派生物への条件・特許条項の要否を聞いて支援する。

本文は**テンプレートから取得する**（記憶から書かない）。GitHub では `gh repo license view <key>`（例: `mit`）、無ければ `gh api /licenses/<key> --jq .body`。どちらも使えなければ、本文の入手を利用者に頼むか、ライセンス無しで進めて後で足す。
年と権利者（アカウント名、または利用者が指定する名前）を埋めて `LICENSE` に置く。

### 7. `.gitignore`

プロジェクトの言語を利用者に尋ねる（既存のファイルから推定できれば確認だけ）。テンプレートは `gh repo gitignore view <Name>`（名前は大文字小文字を区別する。例: `Python`）、無ければ `gh api /gitignore/templates/<Name> --jq .source`。どちらも使えなければ、その言語の標準的な生成物だけを利用者と相談して書く。

- 既存の `.gitignore` があれば**末尾に追記**する（既にある行は重複して書かない）。
- **既定で、進行根幹ファイル・内部資料置き場・固有指示ファイルを加える**（git 非追跡にする）。利用者が明示的に例外を指示した場合（例: 固有指示ファイルは追跡する）はそれに従う。

### 8. コミットと push

1. 対象ファイルを列挙して確認を取り、コミットする。コミットメッセージの言語は、固有指示ファイル → グローバル指示書 → 利用者に尋ねる、の順で決める。
2. リモートがあれば、**既定ブランチへの push を個別に確認してから**行う（`git push -u origin <既定ブランチ>`。ブランチ名を明示し、`--all` や `--mirror` は使わない）。ローカル完結なら push を省く。
3. push が権限エラーで落ちたら手順2に戻る（アクティブなアカウントの不一致を疑う）。
4. 手順2で一時的にアカウントを切り替えていたら、**ここで元へ戻す**。

### 9. 完了報告

最終の状態表（全項目が「整っている」）、作成・変更したファイル、リモートの URL、使うアカウント、残る作業（他エージェント向けファイルの作成提案、リモート側の設定など）を報告する。アカウントを切り替えていたら、戻したことを明記する。

## 再実行と中断からの再開

各手順が「調べてから不足だけ行う」形なので、**再実行は常に手順0から始めればよい**。再開専用の分岐は無い。
途中で止まった中間状態（例: `git init` 済みでリモート未作成、ファイルは作ったが未コミット）は、状態表の「要対応」として自然に拾われる。
全項目が整っていれば「作業不要」で終わる。これが再入可能であることの判定条件である。

## データ

### エージェントとファイル名の表

| エージェント | 固有指示ファイル | ホスティング CLI の例（GitHub） |
|---|---|---|
| Claude Code | `CLAUDE.md` | `gh` |
| OpenAI Codex | `AGENTS.md` | `gh` |
| OpenCode | `AGENTS.md` | `gh` |

表に無いエージェントは利用者に尋ねる。GitHub 以外のホスティングサービスではその CLI に読み替える。

### 固有指示ファイルに書く節の雛形

見出しと印は固定し、各項目の値を埋める。言語は「前提」のとおり。

```
## プロジェクト構成（project-start が管理）
<!-- project-start: managed -->

1. リモートリポジトリ: <host>/<owner>/<repo>（またはローカル完結）。既定ブランチ: <名前>。
2. 使用アカウント: <login>。コミット識別子: user.name=<値> / user.email=<値>。
3. 禁止事項: この PC の OS のログイン名や、上記以外のアカウントでコミット・push しない。
   ホスティング CLI を使う前にアクティブなアカウントを確認し、違えば切り替えて作業後に戻す。
4. 進行根幹ファイル: <path>（git 非追跡）。内部資料置き場: <dir>/（git 非追跡）。
   版ごとの実装計画・実装記録・申し送り文書はここに置く。
5. 根幹ファイルの扱い: ユーザー記載を許可なく消さない。版ごとの詳細は内部資料置き場の計画・記録に書き、
   根幹ファイルには版ごとに目安200字のサマリだけを残す。
6. ライセンス: <名前>（LICENSE ファイル）。
```

## うまくいかないときの確認

- **リモートの URL から所有者が読めない**: SSH のホストエイリアスや自前のホスティング。owner / repo を利用者に確認する。
- **CLI が無い／ログインしていない**: アカウントの照合は利用者への確認に置き換える。`gh auth login` の案内は利用者が自分で行う操作として示す。
- **CLI が認証エラー（401）を返す**: トークンの期限切れ。再ログインを案内する。
- **リモートの作成で「既に存在する」**: 同名のリポジトリがある。別名にするか、既存をリモートに設定する（`git remote add origin <URL>`）。
- **固有指示ファイルの節が二重にある**: 手で足した痕跡。どちらを残すか利用者に確認し、片方を消す（確認なしに消さない）。
- **`.gitignore` に根幹ファイルが別表記で既にある**: 重複を足さない。既存の行が効いていることを `git check-ignore` で確かめる。
