# project-start: 新規プロジェクト開始の定型手順

> **skill version**: 1.0.1

セッション内で初めて本スキルを使用するときは「project-start スキル v1.0.1 を使用します」と宣言する。

新しいプロジェクトのディレクトリについて、リモート、アカウントとコミット識別子、進行根幹ファイルと内部資料置き場の骨格、ライセンス、`.gitignore`、プロジェクト固有指示ファイルを整え、初回コミットと push までを行うための手順書である。
誤ったアカウントでコミットや push をしてしまう事故、進行根幹ファイルが肥大する問題、プロジェクトごとに構成が揺れる問題を、着手の時点で防ぐ。

## 4つの原則

1. 再入可能にする。各手順は「現状を調べる → 不足だけを行う → 状態表を更新する」の形を取る。完了後や中断後に再実行しても、整っているものには触らない。
2. 承認を求めるのは次の4か所に限る。
   - ① `git init`（手順1）。
   - ② ファイルの作成・変更。手順0の表の直後に「行うこと」を列挙して、まとめて1回承認を得る。手順3〜7の書き込みはすべてこの1回に含める。以降は尋ね直さない。
   - ③ コミット（手順8）。対象を示す。
   - ④ リモートへ出る操作（リモートの作成・push）。**その都度個別に**承認を得る。アカウントの切り替えも承認を要する。
3. 尋ねることはまとめる。利用者の判断が要る事項（既定ブランチ名、リモートの扱い、識別子、ファイル名、ライセンス、言語）は、手順0の表の直後に一度に尋ねる。選択肢を示して回答を得られる対話手段があれば、それを使う。手順の途中で1つずつ往復しない。
4. エージェント固有の知識は表に分けて置く。固有指示ファイルの名前と CLI の名前は、「データ」の節の表で引く。手順本体は表に無いエージェントにも通用する形で書く。

## 前提と一般化ルール

- 実行中のエージェントを判別し、固有指示ファイルの名前を「エージェントとファイル名」の表で引く。判別できなければ利用者に尋ねる。
- ホスティングサービスは GitHub を例に書く。CLI は表の列で引き、他のサービスではその CLI に読み替える。CLI が無ければ、所有者・アカウントは利用者に尋ねる。
- リモートには「所有者を持つもの」と「持たないもの」がある。ホスティングサービス上のリポジトリは所有者（利用者または組織）を持つ。ローカルのベアリポジトリ、`file://`、自前のホストなど、URL から所有者を読めないものは「所有者なし」として扱う。所有者なしでは、アカウントの照合を省き、識別子は利用者の確認だけにする。
- 固有指示ファイルに書く言語は、利用者のグローバル指示書（`CLAUDE.md` / `AGENTS.md` 相当）と同じにする。無ければ尋ねる。
- 既定ブランチ名は次の値を既定案にして尋ねる。
  - リモートがあれば、リモートの HEAD（`git symbolic-ref refs/remotes/origin/HEAD` または `git remote show origin`）
  - 新規に初期化するなら、`git config init.defaultBranch`
  - どちらも無ければ、`main`
- 「進行根幹ファイル」はプロジェクトの方針と版ごとの要約を置く文書である。「内部資料置き場」は版ごとの計画・記録・申し送りを置く、git 非追跡のフォルダである。どちらも名前を**決め打ちしない**。名前はプロジェクトごとに違う（手順4）。
- 引数は不要。

## 手順

### 0. 現状の把握（状態表）と確認

次の項目を一度に調べ、表（項目／現状／判定／根拠／対応する手順）にして示す。判定は「整っている」「要対応」「未判定」の3つとする。git リポジトリの外では、項目2・4・10 を「未判定」とする。

| # | 項目 | 調べ方 | 「整っている」の条件 | 手順 |
|---|---|---|---|---|
| 1 | git リポジトリ | リポジトリの中かどうか（`git rev-parse --is-inside-work-tree`） | リポジトリである | 1 |
| 2 | リモートと所有者 | `git remote -v` の URL から host / owner / repo を読む | リモートがあり所有者が読める。または「所有者なし」「ローカル完結」と固有指示ファイルに記録済み | 1 |
| 3 | CLI のアカウント | CLI のアカウント一覧（GitHub なら `gh auth status`。各アカウントに `Active account: true/false` が出る） | CLI が所有者のアカウントを**保持している**（アクティブかどうかは問わない。リモートへ出る操作のときだけ切り替える）。または所有者なし・ローカル完結 | 2 |
| 4 | コミット識別子 | `git config --local user.name` / `user.email`（無ければ効いている値を `git config user.name` 等で） | 所有者（所有者なし・ローカル完結なら、固有指示ファイルに記録した使用アカウント）に対応する値がローカル設定にあり、OS のログイン名が混じっていない（アカウント名と同じ場合を除く） | 3 |
| 5 | 進行根幹ファイル | 手順4の探索 | 存在し、固有指示ファイルに記載がある | 4 |
| 6 | 内部資料置き場 | 手順4の探索 | 存在し、固有指示ファイルに記載がある | 4 |
| 7 | ライセンス | `LICENSE` / `LICENSE.md` / `COPYING` | 存在する。または「無し」と固有指示ファイルに記録済み | 5 |
| 8 | `.gitignore` | ファイルの有無と既定3項目（進行根幹ファイル・内部資料置き場・固有指示ファイル） | 存在し、既定3項目（固有指示ファイルに例外の記録があればそれに従う）を含む | 6 |
| 9 | 固有指示ファイル | 表の名前のファイルと、本スキルの節の印（手順7） | 節があり、内容が項目2〜8と一致 | 7 |
| 10 | 未コミット・未 push | `git status`、上流があれば未 push のコミット | どちらも無い | 8 |

すべて「整っている」なら、「作業不要」と報告して終わる。そうでなければ、次の順に進める。

1. 利用者の判断が要る事項（原則3）を一度に尋ねる。表で「要対応」「未判定」になった項目に関わるものだけでよい。
2. 答えを得たら、「行うこと」（作る・変えるファイルと、その内容の要点）を列挙し、まとめて1回承認を得る（原則2の②）。
3. 該当する手順だけを 1 → 8 の順に行い、整っている手順は飛ばす。

### 1. リポジトリの由来とリモート

由来を3つに分ける。

- **(a) 非 git**: `git init` を提案して承認を得る（原則2の①）。既定ブランチ名は「前提」のとおり。初期化後は (c) へ。
- **(b) リモートあり**: URL から host / owner / repo を読む。`git@host:owner/repo.git` と `https://host/owner/repo(.git)` の両形式を読む。
  SSH のホストエイリアス（`git@github-xxx:owner/repo.git` のような形）では owner / repo だけが確実なので、host は利用者に確認する。
  ローカルのパス・`file://`・自前のホストなど所有者を読めない URL は「所有者なし」とし、手順7で記録する。
- **(c) git あり・リモート無し**: 手順0で尋ねた答えに従う。
  - リモートを作る → 可視性（private を既定案）、名前（ディレクトリ名を既定案）、作成に使うアカウントを決める。手順2を先に通してから、**個別に承認を得て**作る（原則2の④）。
    GitHub なら `gh repo create <owner>/<name> --source . --remote origin --private`（または `--public`）。push は手順8で行う。
    `--source` はライセンスや `.gitignore` のテンプレート指定と併用できないので、それらは手順5・6でローカルに作る。
  - 既存のリモートを設定する（別ホスト・ローカルのベアリポジトリなど）→ `git remote add origin <URL>` を行い、以後は (b) として扱う。
  - ローカル完結 → 手順7で「ローカル完結」と記録する。手順2の照合は省き、手順3は利用者が使う名前とメールの確認だけにする。

### 2. アカウントの照合

所有者を持つリモート（手順1）のときだけ行う。ホスティング CLI は複数のアカウントを保持し、そのうち1つがアクティブという構成を取れる。アクティブなアカウントが所有者と違うと、リモートの作成や push が権限エラーで失敗する。

1. CLI のアカウント一覧とアクティブなアカウントを読む（GitHub なら `gh auth status`）。
2. 所有者のアカウントを保持しているなら、それを「このプロジェクトで使うアカウント」にする。アクティブでなくても、ここでは切り替えない。リモートへ出る操作（手順1(c) の作成、手順8の push）の直前に、**承認を得てから切り替える**。操作が終わったら、**成否にかかわらず必ず元へ戻す**。戻す操作に承認は要らない。戻したことは手順9で報告する。承認が得られなければ、その操作を行わず、未了として報告する。
3. 保持していない（利用者がコラボレータとして別のアカウントで操作する場合など）なら、利用者が指定するアカウントを「使うアカウント」にする。権限の有無は実際のリモート操作で分かる。失敗したら報告する。
4. 所有者が組織かどうかは、GitHub では `gh api users/<owner> --jq .type` が `Organization` かどうかで分かる。所有者が組織なら、使うアカウントがその組織で操作できるかを、CLI で確認できる範囲で確かめる（`gh repo view <owner>/<repo> --json viewerPermission` など）。確認できなければ「未確認」と書き、利用者に確認する。
5. 決めたアカウントを状態表に残す（手順7で固有指示ファイルに書く値になる）。

CLI が無い、または GitHub 以外でアカウントを読めない場合は、使うアカウントを利用者に尋ねる。推測で埋めない。

### 3. コミット識別子

ローカル設定の `user.name` / `user.email` を読む。未設定なら、グローバル設定から効いている値を「現在効いている値」として示す。次の順で照合する。

1. 名前が手順2のアカウント名、または利用者が認めた表示名か。
2. メールがそのアカウントに紐づくものか。GitHub では noreply 形式 `<id>+<login>@users.noreply.github.com` を既定案にする。`id` は `gh api users/<login> --jq .id` で読め、アクティブなアカウントに依存しない。2017年7月より前のアカウントは `<login>@users.noreply.github.com` のこともある。GitHub 以外では利用者に尋ねる。利用者が別のメールを使うなら、それを認める。
3. 名前またはメールに **OS のログイン名**（`whoami` 相当）が混じっていないか。混じっていれば警告する（アカウント名と同じ場合を除く）。

不一致・未設定なら、手順0で得た答えに従って **`git config --local user.name` / `user.email` に書く**（原則2の②に含まれる）。グローバル設定は変えない。所有者なし・ローカル完結なら、利用者が使う名前とメールを確認して書く。

### 4. 進行根幹ファイルと内部資料置き場

次の順で探す。1と2で明らかなら、確認せずに採用する。

1. 利用者のグローバル指示書に名前が書かれていればそれ（例: 進行根幹ファイルの名前、内部資料のフォルダ名）。
2. 既存の固有指示ファイルに書かれていればそれ。
3. ディレクトリ内の候補（進行・計画・ロードマップの語を持つ Markdown、資料・docs の名を持つフォルダ）。候補があれば手順0で確認する。

無ければ、名前の既定案を利用者の言語と慣行に合わせて提案し、手順0で尋ねる（名前を決め打ちしない）。作るのは、進行根幹ファイル1つ（表題と「この文書の役割」の数行、要望欄の見出し）と、内部資料置き場のフォルダ1つ（空）である。

### 5. ライセンス

`LICENSE` / `LICENSE.md` / `COPYING` を探す。**あればそれに従い**、名前を状態表に記す（手順7で固有指示ファイルに書く）。
無ければ、手順0で尋ねた答え（MIT / Apache-2.0 / GPL-3.0 / 非公開のため無し / その他）に従う。尋ねるときに相談があれば、公開の有無、派生物への条件、特許条項の要否を聞いて支援する。

本文は**テンプレートから取得する**。記憶から書かない。GitHub では `gh repo license view <key>`（例: `mit`）を使い、無ければ `gh api /licenses/<key> --jq .body` を使う。どちらも使えなければ、本文の入手を利用者に頼むか、ライセンス無しで進めて後で足す。
年と権利者（アカウント名を既定案にして手順0で尋ねる）を埋めて `LICENSE` に置く。

### 6. `.gitignore`

プロジェクトの言語は手順0で尋ねる。既存のファイルから推定できれば、確認だけにする。テンプレートは `gh repo gitignore view <Name>` で取得し、無ければ `gh api /gitignore/templates/<Name> --jq .source` を使う。テンプレートの名前は大文字小文字を区別する（例: `Python`）。どちらも使えなければ、その言語の標準的な生成物だけを利用者と相談して書く。

- 既存の `.gitignore` があれば、**末尾に追記**する。追記するのはテンプレートの行のうち無いものと、下の既定3項目である。既にある行は重複して書かない。
- 既定で、**進行根幹ファイル・内部資料置き場・固有指示ファイルを加え**、git 非追跡にする。利用者が明示的に例外を指示した場合（例: 固有指示ファイルは追跡する）は、それに従い、手順7で例外を記録する。
- 既に git で追跡されているファイルは、ignore に書いても効かない。その旨を報告し、追跡を外すかは利用者に委ねる。勝手に追跡を外さない。

### 7. プロジェクト固有指示ファイル

「エージェントとファイル名」の表から名前を引く。手順2〜6で決まったアカウント、識別子、進行根幹ファイル、内部資料置き場、ライセンス、ignore の例外の値を、ここで書く。そのため、この手順は手順6の後に置いてある。

- 無ければ、下の「固有指示ファイルに書く節の雛形」から作る。
- あれば、本スキルの節の印（見出し `## プロジェクト構成（project-start が管理）` と、その直下の `<!-- project-start: managed -->` の行）を探す。
  - 印が無ければ、節を末尾に追記する。**既存の文は書き換えない**。
  - 印があれば、現在値との差分を示して節の中だけを書き換える。差分の承認は原則2の②の1回に含める。
- 固有指示ファイルが git で追跡されている（他の人と共有するリポジトリなど）なら、アカウント名とメールの値は書かず、「使用アカウントと識別子は各自の手元設定に従う」と書く。個人の識別子を他人のリポジトリへ push しない。
- 他のエージェント向けのファイル（表の他の行）は、**同内容で作ることを提案するだけ**にする。利用者が望めば作る。

### 8. コミットと push

1. 対象ファイルを列挙して承認を得て（原則2の③）、コミットする。コミットメッセージの言語は、固有指示ファイル → グローバル指示書 → 利用者に尋ねる、の順で決める。
2. リモートがあれば、**既定ブランチへの push は個別に承認を得てから**行う（原則2の④）。コマンドは `git push -u origin <既定ブランチ>` で、ブランチ名を明示する。`--all` や `--mirror` は使わない。ローカル完結なら push を省く。
3. 使うアカウントがアクティブでなければ、push の直前に承認を得て切り替え（手順2）、push の後に戻す。
4. push が権限エラーで失敗したら、アクティブなアカウントの不一致を疑い、手順2の規定で切り替えてから push をやり直す。それでも失敗したら、未了として報告する。

### 9. 完了報告

最終の状態表（全項目が「整っている」）、作成・変更したファイル、リモートの URL、使うアカウント、残る作業（リモート側の設定、追跡を外すかの判断など）を報告する。アカウントを切り替えていたら、戻したことを明記する。

## 再実行と中断からの再開

各手順が「調べてから不足だけ行う」形なので、再実行は常に手順0から始めればよい。再開専用の分岐は無い。
途中で止まった中間状態（例: `git init` 済みでリモート未作成、ファイルは作ったが未コミット）は、状態表で「要対応」になる。
全項目が整っていれば「作業不要」で終わる。これが再入可能であることの判定条件である。アカウントの切り替えは操作の間だけなので、戻した後に再実行しても項目3は「整っている」のままになる。

## データ

### エージェントとファイル名の表

| エージェント | 固有指示ファイル | ホスティング CLI の例（GitHub） |
|---|---|---|
| Claude Code | `CLAUDE.md` | `gh` |
| OpenAI Codex | `AGENTS.md` | `gh` |
| OpenCode | `AGENTS.md` | `gh` |

表に無いエージェントは利用者に尋ねる。GitHub 以外のホスティングサービスではその CLI に読み替える。

### 固有指示ファイルに書く節の雛形

見出しと印は固定し、各項目の値を埋める。言語は「前提」のとおり。

```
## プロジェクト構成（project-start が管理）
<!-- project-start: managed -->

1. リモートリポジトリ: <host>/<owner>/<repo>（所有者なしの URL、またはローカル完結）。既定ブランチ: <名前>。
2. 使用アカウント: <login>。コミット識別子: user.name=<値> / user.email=<値>。
   （このファイルを git で追跡する場合は「各自の手元設定に従う」とだけ書く）
3. 禁止事項: この PC の OS のログイン名や、上記以外のアカウントでコミット・push しない。
   ホスティング CLI を使う前にアクティブなアカウントを確認し、違えば切り替えて作業後に戻す。
4. 進行根幹ファイル: <path>（git 非追跡）。内部資料置き場: <dir>/（git 非追跡）。
   版ごとの実装計画・実装記録・申し送り文書はここに置く。追跡の例外: <無し／固有指示ファイルは追跡 など>。
5. 根幹ファイルの扱い: ユーザー記載を許可なく消さない。版ごとの詳細は内部資料置き場の計画・記録に書き、
   根幹ファイルには版ごとに目安200字のサマリだけを残す。
6. ライセンス: <名前>（LICENSE ファイル）、または「無し」。
```

## うまくいかないときの確認

- リモートの URL から所有者が読めない: SSH のホストエイリアスなら owner / repo を利用者に確認する。ローカルのパスや自前のホストなら「所有者なし」として進める。
- CLI が無い／ログインしていない: アカウントの照合は利用者への確認に置き換える。`gh auth login` の案内は利用者が自分で行う操作として示す。
- CLI が認証エラー（401）を返す: トークンの期限切れ。再ログインを案内する。
- リモートの作成で「既に存在する」: 同名のリポジトリがある。別名にするか、既存をリモートに設定する（手順1(c) の2つ目）。
- 固有指示ファイルの節が二重にある: 手で足した痕跡。どちらを残すか利用者に確認し、片方を消す。確認なしに消さない。
- `.gitignore` に進行根幹ファイルが別表記で既にある: 重複を足さない。既存の行が効いていることを `git check-ignore` で確かめる。
- 再実行のたびにアカウントの切り替えを求められる: 項目3の条件は「保持している」であり、「アクティブである」ではない。切り替えを求めるのはリモートへ出る操作の直前だけである。
