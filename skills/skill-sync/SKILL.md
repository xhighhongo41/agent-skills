# skill-sync: 導入済みスキルの一覧と更新

> **skill version**: 1.3.0

セッション内で初めて本スキルを使用するときは「skill-sync スキル v1.3.0 を使用します」と宣言する。

同じスキルを複数のコーディングエージェントへ配っていると、どこにどの版が入っているかが分からなくなり、
一部だけ古いまま放置される。本スキルは**導入済みスキルの版を一覧し、配布元の最新版と突き合わせ、
ユーザーが選んだ対象だけを更新する**ための手順書である。

**このスキルは利用者のホームディレクトリ配下に書き込む。**したがって
**更新の適用はユーザーの承認を得てから行う**。承認なしにファイルを置き換えてはならない。

## 書き込みの範囲（最優先の制約）

**本スキルが書き込むのは、本スキルを実行しているエージェント自身のコンフィグディレクトリ配下に限る。**
それ以外の場所への書き込みは、**ユーザーが明示的にその場所を指示した場合を除き、行ってはならない。**

他のエージェントのスキルが古いと分かっても、**こちらから書き換えない**。
別のエージェントの設定を勝手に触ることは、利用者が本スキルに委ねた範囲を超える。
更新が必要なら、**そのエージェント上で本スキルを実行してもらう**。

自分がどのエージェントとして動いているかが判別できない場合は、**書き込まない**。
判別できない旨を伝え、以降の適用はユーザーの指示を待つ。

## 前提と一般化ルール

- **エージェントの種類をハードコードしない。** 後述の「既知のエージェント」表は*データ*であり、
  手順そのものは表に無いエージェントにも通用する形で書いてある。表に載っていないエージェントを
  使っている場合は、汎用探索（手順2）で拾う。
- スキルの版は `SKILL.md` の frontmatter の `metadata.version` に入っている。
  **これが無いスキルは「版不明」として扱い、エラーにしない**。古い配布物には版が入っていない。
- 配布元は `index.json` という1ファイルで表現される。**どの URL を使うかは手順1で決める。**
  下記は**既定値**であり、**利用者の設定があればそちらが優先する**。

  ```
  https://raw.githubusercontent.com/xhighhongo41/agent-skills/main/skills/index.json
  ```

- **スキルには対象エージェントが決まっているものがある。** `SKILL.md` の frontmatter の
  `compatibility` に対象が列挙されており、**このキーが無いスキルは全エージェント向け**である。
  対象外のスキルを入れても多くのエージェントは黙って読み込んでしまうため、
  **気づかないまま使えないスキルが混ざる**。これを防ぐのも本スキルの役目である。
- **判定と適用を混ぜない。** まず全体を一覧して見せ、対象を選ばせ、承認を取ってから書き込む。
- **版が一致していても内容が違うことがある**（手元で改造した、配布元が版を上げずに直した）。
  本スキルは版に加えて**内容も照合する**（手順3の「内容の照合」）。

## 手順

### 1. 配布元を決めて最新版を取得する

**まず、配布元の URL を利用者の設定から読む。** リモートから自動でスキルを取得する仕組みを持つ
エージェントは、**その取得元を自分の設定ファイルに書いている**（表の下の「配布元の設定の在処」）。
**そこに URL があればそれが正であり、既定値より優先する。** 設定を持たないエージェント、
または設定が見つからない場合は既定値を使う。

**どちらの URL と比較したかを一覧に明示する。** ここを取り違えると、**比較の基準が実際の配布元とずれる**。
機構が取得したキャッシュは利用者の設定した配布元から来ているので、既定値と突き合わせると
「ローカルが新しい」「配布元に無い」といった**誤った状態が一覧に並ぶ**。
どちらを見たかが書いてあれば、利用者はその食い違いに気づける。

決まった URL の `index.json` を取得し、`skills[]` の各要素から `name` / `version` / `files` / `compatibility` を読む。
`files` はスキルフォルダ内の全ファイルの相対パスであり、**更新時に取得すべきファイルの一覧そのもの**である。

各ファイルの取得先は `{index.json を置いている URL のディレクトリ}/{name}/{files の各パス}` で決まる。

**`compatibility` があれば、そのスキルは列挙されたエージェント専用**である。無ければ全エージェント向けとして扱う。
配布元によってはこの値を持たないことがある（古い配布物や、別の生成規則を採る配布元）。
その場合は**手順5で取得する `SKILL.md` の frontmatter から読む**ので、ここで欠けていてもエラーにしない。

取得に失敗した場合（オフライン、URL 誤り、配布元の障害）は**そこで止めない**。
「配布元に接続できなかった」と明示したうえで、手順2〜3のローカル一覧までを実行して報告する。
その状態では更新の要否は判定できないので、**更新の適用には進まない**。

### 2. 導入済みスキルを走査する

**まず、本スキルを実行しているエージェント自身のコンフィグディレクトリを走査する。**
これは更新の対象になりうる唯一の場所であり、ここを見ないと本スキルは目的を果たせない。

あるエージェントのスキルの置き場所は、次の順で決める。

1. **環境変数による上書きを最優先する。** 表の「環境変数による上書き」欄の変数が設定されていればそちらを使う。
2. 「既知のエージェント」表のパスを引く。
3. **表に無いエージェント、または表のパスが存在しない場合は汎用則で探す。**
   ほとんどのエージェントはスキルを `<そのエージェントの設定ディレクトリ>/skills/<スキル名>/SKILL.md`
   に置く（`skills` が単数形 `skill` の実装もある）。設定ディレクトリの場所は
   そのエージェントの文書か、ホーム直下のドットディレクトリから判断する。

見つけた各ディレクトリの直下を1階層だけ列挙し、`<スキル名>/SKILL.md` があるものをスキルとみなす。
`SKILL.md` から frontmatter の `name` と `metadata.version` と `compatibility` を読む。

**互換読み込みで見えるディレクトリも走査する。** エージェントによっては、自分の置き場に加えて
**他のエージェントの置き場も読む**（「既知のエージェント」表の下の「互換読み込み」）。そこにあるスキルは
**実行中のエージェントから既に使える**。ここを見ないと、**既に使えるスキルを「未導入」と表示して、
利用者に二重導入させてしまう。**

- **一覧には出すが、書き込まない**（「書き込んではいけない場所」を参照）。実体の持ち主が別のエージェントだからである。
- **どのエージェントの持ち物かが分かるように示す。**「自分から見えているが、実体は別のエージェントの
  ディレクトリにある」と伝われば、利用者は二重に入れずに済む。

**配布経路で取得したスキルも走査する。** エージェントが配布元から自動で取得したスキルは、
利用者が自分で置くディレクトリとは**別のキャッシュ**に入ることがある（表の「配布キャッシュ」欄）。
ここを見ないと、**配布経路で入ったスキルが一覧から丸ごと抜ける**。

- **一覧には出すが、更新の対象にはしない**（「書き込んではいけない場所」を参照）。
  この領域はエージェントの機構が管理しており、手で書き換えても次の取得で置き換わる。
- キャッシュには**取得時の版を記録したファイル**が置かれることがある。
  **記録された版と `SKILL.md` の `metadata.version` の両方を読み、食い違えば「版不明」として扱う。**
  機構が自分で作る状態ではないため、手で上書きされた可能性を知らせる価値がある。
- **同じスキルがユーザースコープとキャッシュの両方にあれば、別行として両方出す。**
  実体が別のファイルなので名寄せしない。どちらがエージェントに読まれるかは機構が決めるため、
  **本スキルは「二重に存在する」ことを知らせるに留める。**

走査で守ること:

- **エージェント本体が管理する領域は走査から除外する**（「書き込んではいけない場所」を参照）。
  利用者のスキルではないため、一覧に出す意味がない。
- **同じ実体を二重に数えない。** 複数のエージェントが同じディレクトリを読む構成があるため
  （表の「互換読み込み」欄を参照）、実パスで名寄せする。
- プロジェクトスコープのスキル（作業中のリポジトリ配下）は、**ユーザースコープとは別行**として扱う。
  リポジトリの持ち物なので、勝手に更新しない。

### 3. 比較して一覧を提示する

まず版を比べ、版が一致した行については**内容も照合する**（下の「内容の照合」）。
エージェント × スキルの表にして、状態を次の8種で示す。

| 状態 | 意味 | 既定の扱い |
|---|---|---|
| 最新 | ローカルと配布元の版が一致し、**内容も一致** | 何もしない |
| 更新あり | 配布元の版が違う | **更新候補** |
| 未導入 | 配布元にあり、**実行中のエージェントからはどこにも見えない**（自分の置き場・互換読み込み・配布キャッシュのいずれにも無い） | **導入候補**（ユーザーが望む場合のみ） |
| 対象外 | `compatibility` に、実行中のエージェントが含まれない | **導入・更新の候補から外す。**理由を添えて一覧には出す |
| 版不明 | ローカルに `metadata.version` が無い、または配布キャッシュの記録と食い違う | **更新候補**（古い配布物か、手で上書きされた可能性） |
| ローカルが新しい | ローカルの版が配布元より進んでいる | **更新しない。** 手元で改造した可能性があるので必ず知らせる |
| 内容が違う | 版は一致するが、`files` のいずれかの内容が配布元と違う、または欠けている | **既定では候補に入れない。** 違うファイル名と差分の規模を示し、含めるかを個別に確認する |
| 配布元に無い | ローカル固有のスキル | 触らない |

配布元の版は**文字列として比較する**。大小関係の判定に頼らず、「一致しない＝更新候補」とする。
「ローカルが新しい」の判定だけは版番号を数値として読み、判断がつかなければ「版が食い違う」と報告する。

**内容の照合。** 版が配布元と一致した行すべて（自分の置き場・互換読み込みで見える場所・配布キャッシュ・プロジェクトスコープ）が対象である。
「更新あり」「ローカルが新しい」「版不明」「対象外」「配布元に無い」の行は照合しない（既に別の状態が付いており、「更新あり」は取り直しで解消する）。

- 配布元から、そのスキルの `files` に挙がる**全ファイル**を取得する。**手順5と同じ取得手段を使う。**
  内容をそのまま得られる手段でなければ比較にならない（要約や整形を挟む取得手段は使わない）。
- ファイルごとに、**改行コードと末尾の改行の有無を揃えてから**、内容の要約値（ハッシュ）または全文で比べる。
  それ以外の違いはすべて「違う」とする。
- **1ファイルでも違えば、または `files` にあるファイルが手元に無ければ「内容が違う」**。
  手元にあって `files` に無いファイルは、ここでは見ない（手順5で消さずに報告する）。
- `files` を持たない配布元（古い配布物）は `SKILL.md` だけ比べる。
- 配布元に接続できないときは照合しない（手順1のとおり、更新の要否は判定できない）。
- 一覧には**違うファイル名と差分の規模**（違う行数の目安）を添える。

**対象エージェントの判定。** `compatibility` に実行中のエージェントが含まれるかどうかで決める。
自分がどのエージェントとして動いているかは、「既知のエージェント」表の `compatibility` の値の列で引く。

- **「対象外」は他の状態より優先する。** 版が古かろうと新しかろうと、対象でないなら更新も導入もしない。
- **対応付けができない場合は判定しない。** 表に無いエージェントで動いている、あるいは自分が
  どのエージェントか判別できない場合は、**対象外と決めつけず**、判定できない旨を示したうえで
  導入候補から外し、判断を利用者に委ねる。誤って「対象外」と出すと、使えるはずのスキルを遠ざけてしまう。
- **既に導入済みのスキルが対象外だった場合は、勝手に消さずに知らせる。**
  利用者が意図して置いた可能性がある。

### 4. 更新対象を選ぶ

**黙って全件更新してはならない。** 一覧を見せたうえで、何を更新するかを決めてもらう。

**更新の候補にできるのは、自エージェントのコンフィグディレクトリ配下にあるものだけ**である
（「書き込みの範囲」を参照）。それ以外は一覧に出ていても候補から外し、
**そのエージェント上で本スキルを実行するよう案内する**。

呼び出し時の引数でスキル名やエージェント名が指定されていればそれを対象とする。
指定が無ければ候補を提示して選択を促す。選択の粒度は次の3つを受け付ける。

- **スキル単位**（例: あるスキルだけを全エージェントで更新する）
- **エージェント単位**（例: あるエージェントだけを最新に揃える）
- **その組み合わせ**、および「更新候補すべて」

「ローカルが新しい」ものは既定で対象から外す。**上書きするとユーザーの改造が消える**ため、
含めるかどうかを個別に確認する。

**「内容が違う」ものも既定で対象から外す**（「ローカルが新しい」と同じ）。含めるかは1件ずつ確認し、
確認のときに差分（または規模）を示す。上書きすると手元の変更が消える。
手元の改造を残したいなら、その改造を配布元へ反映して版を上げるよう案内する。

**「対象外」のものも既定で対象から外す。** 利用者が明示的に含めたいと言った場合は、
**そのエージェントでは動かない見込みであること**を伝えたうえで判断に従う。
配布側が対象を宣言しているだけで、実行を妨げる仕組みがあるわけではないため、
入れること自体は可能である。

### 5. 更新を適用する

**書き込む前に、書き込み先が自エージェントのコンフィグディレクトリ配下であることを確認する。**
範囲外のものが混じっていたら、**ユーザーがその場所を明示的に指示していない限り書き込まない**。
指示が無ければ、その1件を適用せずに「どこへ書けなかったか」を報告する。

**承認は、書き込みを始める直前に1度だけ求める。** 何をどこへ書くかを一覧で示してから尋ねる。
承認が得られたら、選ばれた対象の範囲内では**1件ずつ聞き直さずに最後まで実行してよい**。

対象1件ごとに次を行う。

1. 配布元から、そのスキルの `files` に挙がっている**全ファイル**を取得する。
   `SKILL.md` だけでなく、付属のメタデータファイルや参照文書も含めて取得する。
2. 取得がすべて成功してから配置する。**部分的に取得できた状態で書き始めない**
   （途中で失敗すると、中途半端に混ざったスキルフォルダが残る）。
3. **取得した `SKILL.md` の `compatibility` を、配布元の一覧の値と突き合わせる。**
   - **食い違っていたら、その1件は配置しない。** 両方の値を示してユーザーに確認を求める。
     一覧は生成物であり、再生成漏れや配布元のブランチ違いで実体とずれることがある。
     **ずれたまま書き込むと、対象外のスキルを入れてしまう。**
   - 一覧に `compatibility` が無かった場合は、**ここで読んだ値で判定する**。
     その結果それが対象外と分かったら、**配置せずに知らせる**。
   - **残りの対象は続けてよい。** 取得の失敗と違い、これは配置前に分かる食い違いである。
4. 配置先のスキルフォルダへ上書きする。
5. **配布元に無いファイルがフォルダに残っている場合は、消さずに報告する。**
   利用者が意図して置いたファイルかもしれない。削除は別途確認を取る。
6. 配置後に `SKILL.md` を読み直し、`metadata.version` が配布元の版と一致することを確認する。

**途中で失敗したら、そこで残りを止める。**「どこまで適用したか」「どれが未適用か」を必ず報告する。
部分的に適用された状態を隠してはならない。

### 6. 結果を報告する

適用したもの・スキップしたもの・失敗したものを分けて示す。
失敗があれば原因と、次に取るべき手段（再実行、手動コピー、配布元の確認）を添える。

## 既知のエージェントのスキルディレクトリ

**この表はデータである。**内容は古くなりうるので、表のパスが存在しなければ手順2の汎用則へ落とす。

| エージェント | ユーザースコープ | 配布キャッシュ | `compatibility` の値 | 環境変数による上書き |
|---|---|---|---|---|
| Claude Code | `~/.claude/skills/` | プラグイン機構が管理（下記） | `claude-code` | `CLAUDE_CONFIG_DIR` |
| OpenAI Codex | `~/.codex/skills/` | 未調査 | `codex` | `CODEX_HOME` |
| OpenCode | `~/.config/opencode/skills/` | `~/.cache/opencode/skills/` | `opencode` | `XDG_CONFIG_HOME` / `OPENCODE_CONFIG_DIR`（キャッシュは `XDG_CACHE_HOME`） |

**確認の根拠**: ユーザースコープの3件はいずれも実機で確認した。Codex の公式文書はベンダ中立の
`~/.agents/skills/` も挙げるが、実機には未生成だった。OpenCode は単数形の `skill/` も受理する。
OpenCode の配布キャッシュには、取得時の版を記録した `.opencode-version` がスキルごとに置かれる。

**`compatibility` の値の列**は、配布側がスキルの対象を宣言するときに使う語である。
**この対応付けができないエージェントで動いている場合は、対象かどうかを判定しない**（手順3）。

**配布元の設定の在処**（手順1で読む）:

| エージェント | 設定ファイル | キー | 値の形 |
|---|---|---|---|
| OpenCode | `~/.config/opencode/opencode.json` または `opencode.jsonc` | `skills.urls` | `index.json` を**含むディレクトリ**の URL（配列）。末尾のスラッシュは有っても無くてもよい |
| Claude Code | 未調査 | — | — |
| OpenAI Codex | 未調査 | — | — |

**未調査の欄を推測で埋めない。** 設定が見つからないエージェントでは既定値を使い、そう明示すればよい。
設定ファイルはコメントや末尾カンマを含むことがあるので、**厳格な JSON パーサで読めなくても異常ではない**。

Windows では `~` をユーザープロファイル（`%USERPROFILE%`）に読み替える。
OpenCode は Windows でも `~/.config/opencode/` を使う点に注意する（確度は中程度なので、
無ければ汎用則で探す）。

**互換読み込み**: OpenCode は自分のディレクトリに加えて `~/.claude/skills/` と `~/.agents/skills/`
も読む。したがって Claude Code 側へ入れたスキルは OpenCode からも見えており、
**両方へコピーすると二重に見える**。一覧では実パスで名寄せし、
「1か所にあり2つのエージェントから見えている」ことが分かるように示す。

**プロジェクトスコープ**: `.claude/skills/` / `.opencode/skill(s)/` / `.agents/skills/` を
作業中のリポジトリ配下に持つ構成がある。一覧には出すが、更新の既定対象にはしない。

## 書き込んではいけない場所

- **自エージェントのコンフィグディレクトリの外側すべて**（「書き込みの範囲」）。
  ユーザーがその場所を明示的に指示した場合のみ例外とする。
- **他のエージェントが所有するスキルディレクトリ。**
  互換読み込みによって自分から見えていても、**実体の持ち主が自分でなければ書かない**。
  例えば OpenCode は `~/.claude/skills/` を読むが、そこは Claude Code の持ち物である。
- **エージェント本体が管理する領域。** 例えば Codex は自身のシステムスキルを
  `~/.codex/skills/.system/` に置き、目印のマーカーファイルを持つ。
  **走査対象からも外す**（利用者のスキルではないため一覧に出す意味がない）。
- **プラグイン機構の管理下。** Claude Code のプラグイン経由で入ったスキルは
  `~/.claude/plugins/` 配下のキャッシュにあり、ユーザースコープのスキルディレクトリには現れない。
  ここを直接書き換えても次の更新で消える。**一覧には「プラグイン経由」として出し、
  更新はプラグイン機構のコマンド（`/plugin marketplace update <マーケットプレイス名>` など）を案内する。**
- **配布経路のキャッシュ。** 配布元から自動で取得したスキルの置き場（OpenCode の
  `~/.cache/opencode/skills/` など）。ここを手で書き換えても、**次の取得で置き換わる**。
  **一覧には「配布経由」として出し、更新は配布元の版が上がるのを待つか、
  機構に取り直させるよう案内する。**
- 迷ったら書かない。**書き込み先が利用者の意図した場所かどうか確信が持てない場合は、
  適用せずに手順だけを提示してユーザーに委ねる。**

## うまくいかないときの確認

- **スキルが一覧に出ない**: そのエージェントが単数形 `skill/` を使っていないか、
  設定ディレクトリが環境変数で移動されていないかを確認する。
- **更新したのにエージェントが古い版を使う**: 多くのエージェントは起動時にスキルを読む。
  再起動を案内する。キャッシュを持つ機構ではキャッシュの更新も必要になる。
- **「内容が違う」と出た**: 手元で改造したか、配布元が版を上げずに直したかのどちらか。本スキルには見分けられないので、
  差分を見て判断する。改造を残すなら更新しない（その改造を配布元へ反映して版を上げるのがよい）。
  配布元を正とするなら、その1件を含めて取り直す。
- **同じスキルが2行出る**: ユーザースコープと配布キャッシュの両方に実体がある。
  どちらがエージェントに読まれるかは機構が決めるため、本スキルは両方を示すに留める。
  整理するなら、**配布経路に任せるならユーザースコープ側の実体を、手元で管理するなら配布元の設定を**
  見直すよう案内する。
- **配布キャッシュの版が食い違う**: 記録された版と `SKILL.md` の版が違う場合、機構を通さずに
  手で上書きされた可能性が高い。「版不明」として扱い、配布元から取り直すよう案内する。
- **一覧の「配布元版」が、利用者の設定した配布元と合わない**: **手順1の URL の決め方を疑う。**
  利用者の設定を読まずに既定値を使うと、**キャッシュ側が軒並み「ローカルが新しい」になり、
  設定した配布元にしか無いスキルが「配布元に無い」と出る**。一覧に明示した URL が
  利用者の設定と一致しているかを確かめる。
- **対象外だと言われたが使えるはず**: 配布元の一覧が古い可能性がある。その1件の `SKILL.md` を
  直接読んで `compatibility` を確かめる。一覧と食い違っていれば配布元の再生成漏れなので、
  **配布元に知らせる**（手順5の突き合わせが同じ食い違いを捕まえる）。
